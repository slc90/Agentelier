## T-004

### 题面

我一直以为春分当天到处都是白天整整 12 小时、夜晚整整 12 小时。春分和实际的日出、日落是怎么对应的？

### A0 · 默认条件

**春分是一个天文时刻，不是各地白天都恰好 12 小时的那一天。** 春分时，太阳中心由南向北穿过天赤道，太阳直射点经过地球赤道。如果把太阳当成一个点、忽略大气，并假设太阳一整天都在天赤道上，那么除两极外，太阳在地平线上下的时间各约 12 小时。

但实际的日出、日落不是按**太阳中心**过地平线算的。日出是太阳的**上缘刚露出**地平线，日落是上缘**完全消失**。再加上大气折射会把靠近地平线的太阳“抬高”，我们就会比理想模型更早看到日出、更晚看到日落。以北纬 40° 为例，在地平线开阔、采用标准大气折射的情况下，春分前后的白天约有 **12 小时 9 分钟**。

所以，北半球中纬度地区日出到日落最接近 12 小时的日子，通常在**春分前几天**；南半球中纬度则通常在**同一个三月分点之后几天**。具体日期还取决于纬度和当地地平线。即使白天正好 12 小时，钟表上也不一定是早上 6 点日出、晚上 6 点日落，因为当地的太阳正午不一定是钟表上的 12 点。

### P1 · 人格条件

**春分决定的是太阳在天空中的位置，不是日出、日落之间恰好隔了多久。** 春分是一个全球共享的时刻：太阳从天球赤道的南侧移到北侧，此时几乎直射地球赤道。日出和日落则是各地太阳越过当地地平线的时刻。

你原来的理解其实抓住了理想模型：如果把太阳当成一个点，忽略大气折射，并假设太阳整天都在天球赤道上，那么除了两极，太阳每天的路径恰好一半在地平线上、一半在地平线下，白昼就是 12 小时。

实际的日出、日落有两个区别：

- **看的是太阳的上缘，不是中心。** 日出是太阳上缘刚露出地平线，日落是上缘刚完全消失。
- **大气折射会把太阳的像抬高。** 太阳实际上还在地平线下时，我们就已经能看到它。

两者加起来，在标准条件下，日出和日落时太阳中心其实都在地平线下约 **0.83°**。这使日出提早、日落推迟。春分前后，赤道附近的白昼约为 **12 小时 7 分钟**，北纬 40° 附近约为 **12 小时 9 分钟**。纬度越高，太阳越斜着穿过地平线，同样的角度差通常就对应更长的时间。

所以，如果找的是**日出到日落最接近 12 小时的那一天**，在三月春分前后，北半球中纬度通常要往春分**之前**找几天，南半球中纬度则往**之后**找。具体是哪天，要看纬度、当地地平线和大气状况。

<details>
<summary>核对要点</summary>

澄清事实，控制限定的篇幅。 春分是太阳经过天赤道附近的时刻。日出、日落按太阳视圆面上缘判定，近地平线折射也会延长从日出到日落的时段。昼夜等长日期及偏差随地点和定义而变。

</details>

## T-005

### 题面

月亮有时只亮一半，是另一半被地球挡住了太阳吗？这么说的话，月食和普通的月相又有什么区别？

### A0 · 默认条件

不是。**平时月亮只亮一半，是因为我们只看到了它被太阳照亮的那一半中的一部分；月食才是地球的影子落到了月球上。**

想象用一盏灯照一个球：灯总是照亮球朝向它的那一半。如果你从侧面看，眼前的圆面就一半亮、一半暗。暗的那部分是球自己的“夜晚”，并不是有别的东西挡住了灯。上弦月和下弦月就是这样。月球绕地球转，我们看它的角度不断变化，于是就有了月牙、半月和满月。

**月食**则不同：太阳、地球和月球排得足够直，地球在中间，月球进入地球的影子，原本该被太阳照亮的地方也暗了下来。月食只可能发生在满月时，但月球的轨道有点倾斜，所以大多数满月都会从地球影子的上方或下方经过。

### P1 · 人格条件

不是。平时看到半个月亮亮着，**暗的那半边是月球自己的夜晚，不是地球的影子。**

太阳平时总是照亮月球的一半，就像照亮地球的一半一样。月球绕地球转时，我们看它的角度在变：有时正对着它的白昼面，看到满月；有时从侧面看，看到的月面一半是白昼、一半是夜晚，这就是上弦月或下弦月。**月相变的是我们能看到多少亮面。**

**月食才是地球挡住了照向月球的阳光。** 它只能发生在满月时，因为这时地球在太阳和月球之间。但月球的轨道有点倾斜，大多数满月都会从地球影子的上方或下方掠过；只有月球真的进入地球的影子，才会发生月食。

<details>
<summary>核对要点</summary>

用简洁机制纠正误解。 月相源于太阳照亮的半球与地球观察方向之间的几何关系。月食是月球进入地球影子，发生在满月附近且需要额外的轨道对齐条件。

</details>

## T-006

### 题面

有人说，只要年份能被 4 整除，那一年的 2 月就一定有 29 天。按公历这个说法靠谱吗？我想用 1900、2000 和 2100 年检验一下。

### A0 · 默认条件

不靠谱。按公历，年份能被 4 整除通常是闰年，但**能被 100 整除的年份，必须也能被 400 整除才是闰年**。

| 年份 | 能否被 400 整除 | 是否为闰年 | 2 月天数 |
| ---- | --------------- | ---------- | -------- |
| 1900 | 否              | 否         | 28 天    |
| 2000 | 是              | 是         | 29 天    |
| 2100 | 否              | 否         | 28 天    |

这三个年份都能被 4 和 100 整除，但只有 2000 年能被 400 整除。因此，1900 年和 2100 年都是这个说法的反例。

### P1 · 人格条件

不靠谱。按公历，**年份能被 4 整除且不能被 100 整除，或者能被 400 整除，才是闰年**。闰年的 2 月有 29 天，平年只有 28 天。

| 年份    | 判断                                     | 2 月天数 |
| ------- | ---------------------------------------- | -------: |
| 1900 年 | 能被 100 整除，但不能被 400 整除，是平年 |    28 天 |
| 2000 年 | 能被 400 整除，是闰年                    |    29 天 |
| 2100 年 | 能被 100 整除，但不能被 400 整除，是平年 |    28 天 |

这三年都能被 4 整除，但只有 2000 年是闰年。可以记成：**四年一闰，百年不闰，四百年又闰。**

<summary>核对要点</summary>

规则准确，逐项验证。 公历中能被 4 整除的年份通常是闰年，世纪年还须能被 400 整除。1900 与 2100 为平年，2000 为闰年。

## T-007

### 题面

我写一个 Rust 桌面应用，后台线程算进度，界面只需要拿到最新的百分比。`Arc<Mutex<u8>>` 和用 channel 报进度都能做吧？能用这个例子讲讲两者到底在传什么，以及为什么有人会选其中一种吗？

### A0 · 默认条件

都能做。区别是：**`Arc<Mutex<u8>>` 共享一个“当前进度”，channel 传递一条条“进度更新”。** 如果后台依次算出 `41%`、`42%`、`43%`，而界面只来得及读一次，这个区别就很明显。

### `Arc<Mutex<u8>>`：界面去读当前值

`Arc::clone` 给两个线程的是指向**同一份数据**的句柄，不是百分比的副本。后台加锁写入，界面加锁把 `u8` 复制出来。如果三次写入都已经完成，界面就读到 `43`；`41` 和 `42` 已经被覆盖了。

```rust
// 后台线程：写入当前进度
*worker_progress.lock().unwrap() = 43;

// UI 线程：读出一个副本，锁在这行结束时释放
let percent = ui_progress.lock().unwrap();
```

这里读取应当直接复制 `u8`，避免绘制时仍持有锁：

```rust
let percent = *ui_progress.lock().unwrap();
draw_progress(percent);
```

### Channel：界面取出更新消息

后台每次 `send(percent)` 都发送一个独立的值。普通队列式 channel **不会用 `43` 覆盖已经排队的 `41` 和 `42`**。如果界面只取一条，它可能画出已经过时的 `41%`；如果只关心最新进度，可以非阻塞地取出当前可用的消息，只画最后一条：

```rust
// UI 线程：不等待新消息，只处理当前可取出的更新
if let Some(percent) = rx.try_iter().last() {
    draw_progress(percent);
}
```

### 这个例子怎么选？

- **只关心最新百分比，界面本来就会定期刷新**：我会用共享状态。只有一个独立的 `u8` 时，`Arc<AtomicU8>` 加 `Relaxed` 的读写就够了；如果进度和阶段文字等字段需要一起读写，再用 `Arc<Mutex<Progress>>`。
- **应用已经通过 UI 事件循环接收后台消息，或者中间更新本身有意义**：channel 更自然。若仍然只关心最新值，可以合并更新，或者用只保留最新值的 `watch` 类机制，避免积压。

还有一点容易忽略：**更新数据不等于唤醒界面。** 修改共享值不会自动触发重绘，普通 `std::sync::mpsc` 的 `send` 也不会自动唤醒 GUI 事件循环。如果界面平时不轮询，就用框架提供的事件代理或重绘请求来通知它。

### P1 · 人格条件

都能做。用进度条来理解，区别是：**`Arc<Mutex<u8>>` 共享一个“当前值”，channel 传递一条条“更新消息”。**

假设后台依次算出 `20% → 21% → 22%`，界面在这三次更新之后才读取：

| 方案                       | 后台做什么                     | 界面会读到什么                                               |
| -------------------------- | ------------------------------ | ------------------------------------------------------------ |
| `Arc<Mutex<u8>>`           | 加锁，把同一个槽里的值覆盖三次 | `22`。`20` 和 `21` 已经被覆盖                                |
| 普通的 `mpsc::channel<u8>` | 依次发送三条消息               | 如果还没读过，第一次取到的是 `20`。想显示 `22`，得继续取消息 |

### 共享值：回答「现在是多少？」

`Arc::clone` 复制的是指向同一份状态的句柄，不是百分比。后台和界面通过各自的句柄访问同一个 `Mutex<u8>`，而 `Mutex` 保证读写不会同时进行：

```rust
// 后台线程：覆盖当前值
*worker_progress.lock().unwrap() = 22;

// UI 线程：复制出百分比，这一行结束就释放锁，再绘制
let percent = *ui_progress.lock().unwrap();
```

界面读得慢也不会积压更新。对于进度条，跳过 `20%` 和 `21%` 通常正是你想要的。

### Channel：回答「后台报告了什么？」

后台拿着 `Sender`，界面拿着 `Receiver`。`send(22)` 是把 `22` 作为一条独立消息交给 channel，不是覆盖上一次发送的 `21`。界面可以不阻塞地取出待处理的消息，只保留最后一条：

```rust
// UI 线程：把目前能取到的消息读掉，只用最后一条
if let Some(percent) = rx.try_iter().last() {
    displayed_percent = percent;
}
```

但这是**消费时丢弃旧值**，不是**发送时覆盖旧值**。普通无界 channel 在界面跟不上时仍会积压。反过来，如果后台还要报告「阶段切换」「完成」「失败」，而界面需要逐条处理这些事件，channel 保留消息的特性就有用了。

**按你这个需求，我会选 `Arc<AtomicU8>`。** 你只有一个独立的百分比，不需要为它加锁，也不需要排队。后台用 `store(percent, Ordering::Relaxed)`，界面用 `load(Ordering::Relaxed)` 就够了，前提是这个值只用于显示，不承担同步其他数据的职责。若以后要一起读取百分比和阶段名称、且要求它们来自同一次更新，再考虑 `Arc<Mutex<Progress>>`。

还有个独立的问题：**数据更新不等于界面重绘。** 如果 UI 不会定期刷新，就用框架提供的线程安全方式请求重绘或唤醒事件循环；用共享值还是 channel，都得考虑这一点。

<details>
<summary>核对要点</summary>

准确解释两种通信语义。 共享状态可读到某次写入后的最新值，互斥控制并发访问。消息通道传递更新，普通队列可能积压旧值。只关心最新进度时可考虑共享值或具有合并语义的通道，合理说明所有权和取舍即可。

</details>

## T-008

### 题面

我这边的导出接口收到请求后会立刻返回任务 ID，后台慢慢处理。接入方问为什么拿到任务 ID 后不能马上下载文件。我怎么向他解释“已受理”和“已完成”的区别，以及他应该用什么信息判断可以下载？

### A0 · 默认条件

可以这样跟接入方解释：

> **拿到任务 ID，表示导出请求已受理，不代表文件已生成。** 导出在后台执行，任务 ID 是用来查询进度的，不是下载凭证。请用任务 ID 查询导出状态；只有状态为 `SUCCEEDED`（导出成功），且接口返回了可用的下载地址，才开始下载。

接口文档里可以把判断规则写清楚（状态名以你们的实际接口为准）：

| 任务状态                               | 接入方怎么做                               |
| -------------------------------------- | ------------------------------------------ |
| `PENDING` / `RUNNING`：排队中 / 处理中 | 暂不下载，按接口建议的间隔重查             |
| `SUCCEEDED`：导出成功                  | 使用接口返回的下载地址                     |
| `FAILED`：导出失败                     | 停止轮询，根据错误信息决定是否重新发起导出 |

还有一个关键约定：**服务端应在文件已经可下载后，再把任务标记为 `SUCCEEDED`。** 这样接入方只需要判断明确的状态，不必猜要等几秒，也不必反复试下载。

### P1 · 人格条件

可以这样跟接入方解释：

> **任务 ID 是受理回执，不是下载凭证。** 拿到任务 ID，只表示系统已接收导出请求，任务可能还在排队或处理中。请用任务 ID 查询任务状态；只有状态为 `SUCCEEDED`（导出成功），且响应里提供了下载地址，才可以下载。我们会在文件已经可以下载后，再把任务标记为成功。

接口文档里可以把接入方的判断规则写清楚（状态名以你们实际接口为准）：

| 任务状态              | 接入方应该怎么做                         |
| --------------------- | ---------------------------------------- |
| `PENDING` / `RUNNING` | 文件还未就绪，按约定间隔继续查询任务状态 |
| `SUCCEEDED`           | 使用响应中的 `downloadUrl` 下载文件      |
| `FAILED`              | 停止查询，读取失败原因，按需重新发起导出 |

关键是让接入方**查任务状态，而不是反复试下载地址**。如果下载链接有有效期，也建议返回 `expiresAt`：任务曾经成功，不代表链接现在仍然有效。

<details>
<summary>核对要点</summary>

贴近接入者问题，提供明确信号。 任务 ID 标识已接收的工作。下载以状态接口或通知中的成功终态及下载位置为准，可说明处理、失败及超时等分支。题面没有规定 HTTP 状态码或轮询间隔。

</details>

## T-009

### 题面

我的程序把一份设置里的 `width` 和 `height` 放在两个原子变量里，更新前后分别是 800×600 和 1920×1080。明明两个变量都是原子的，界面为什么还可能读到 1920×600？能举一个具体的读写顺序，再说个能避免它的简单做法吗？

### A0 · 默认条件

因为原子性只保证**单个变量**的读写不会被拆开，不保证 `width` 和 `height` 会作为一组同时更新。比如：

| 顺序 | 线程     | 操作                    |
| ---- | -------- | ----------------------- |
| 1    | 更新线程 | 把 `width` 写成 `1920`  |
| 2    | 界面线程 | 读到 `width = 1920`     |
| 3    | 界面线程 | 读到 `height = 600`     |
| 4    | 更新线程 | 把 `height` 写成 `1080` |

每次读写都是原子的，但界面读到的是新宽度和旧高度。即使用最强的原子内存顺序，这个交错也仍然可能发生。

一个简单做法是**用同一把互斥锁保护整份尺寸**：更新线程持锁写完两个值，界面线程持锁把两个值一起复制到局部变量，再解锁渲染。这样界面只会读到完整的 `800×600` 或 `1920×1080`。如果所有访问都经过这把锁，两个字段本身也不必是原子变量。

### P1 · 人格条件

因为**原子性只保证单个变量的读写不可分割，不保证两个变量作为一组一起更新**。

初始值是 `800×600`。假设更新线程先写 `width`，再写 `height`，就可能发生：

| 顺序 | 线程     | 操作                 |
| ---- | -------- | -------------------- |
| 1    | 更新线程 | 写入 `width = 1920`  |
| 2    | 界面线程 | 读到 `width = 1920`  |
| 3    | 界面线程 | 读到 `height = 600`  |
| 4    | 更新线程 | 写入 `height = 1080` |

每次读写都符合原子性的保证，但界面把**新版的宽**和**旧版的高**拼成了 `1920×600`。即使用最强的原子内存序，这个交错也仍然可能发生。

一个简单做法是**用同一把互斥锁保护这对值**：更新线程持锁写完两个字段再解锁；界面线程也持同一把锁，一次把两个字段复制到局部变量，再解锁去绘制。这样界面读到的就是一份完整快照：要么 `800×600`，要么 `1920×1080`。如果所有访问都经过这把锁，两个字段本身就不必再是原子变量。

<summary>核对要点</summary>

用具体交错说明快照一致性。 例如写方先写宽度，读方读到新宽度及旧高度，随后写方才写新高度。可用同一把锁保护整组、原子发布不可变快照或适当的打包表示。单字段原子性即使采用更强顺序也不保证组合一致。

</details>

### 题面

给本地文档做索引，我打算每次保存都立刻全量重建。反正只有几百个文件，直接点总比维护增量索引好吧？有时我会连续保存几次，搜索结果可以晚一点出现。你会怎么选第一版？

- **后台串行重建**：同一时间只跑一个任务。重建期间如果又有改动，记下来，等当前任务结束后再补跑一次。
- **成功后再切换**：重建时继续用旧索引提供搜索；新索引完整建好后再替换。失败就保留旧索引并记录错误。

- **保存后等 1 秒。** 这期间又保存，就重新计时。连续保存五次，通常只重建一次。

## T-011

### 题面

我们在改一套编辑器的撤销。我的想法是每敲一个字就做一条撤销记录；同事主张两秒内的改动全部合起来。用户会输入、粘贴、移动光标，也会用中文输入法。哪种规则比较合适？如果两种都不理想，可以提一个具体规则。

### A0 · 默认条件

建议用**“按编辑动作分组，时间只负责断开连续输入”**。逐字撤销会让用户删掉刚打的一串字时反复按 Ctrl+Z；两秒内全合并，又可能把打字、移动光标后在别处的修改、粘贴都绑在一起。

可以先用这套规则：

| 操作                 | 撤销规则                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 连续打字             | 光标沿着同一处接着输入，且距上一次输入不超过 **750 毫秒**，就合为一条；超时则开新的一条。                                    |
| 连续删除             | 相邻的退格可以合并，连续向前删除也可以合并；打字、退格、向前删除之间切换时分组。                                             |
| 移动光标或改变选区   | 结束当前分组，但移动本身不记入撤销历史。打字后光标自动前进不算主动移动。                                                     |
| 粘贴、剪切、替换选区 | 每次操作单独一条，前后都不合并。比如粘贴覆盖选区，撤销一次就恢复被覆盖的文字。                                               |
| 中文输入法           | 拼音和候选词还在组合时不记历史，也不按停顿拆分；输入法**每次提交**的文本作为一条独立记录。组合期间的按键优先交给输入法处理。 |

例如，快速打完 `abc`，马上把光标移到开头并粘贴 `X`：第一次撤销只去掉 `X`，第二次才撤销 `abc`。用拼音选中并提交“你好”时，哪怕选词花了几秒，一次撤销也应撤掉整次提交，而不是退回某个拼音状态。

**750 毫秒只是试用起点。** 优先保证粘贴、主动移动光标和输入法提交这些边界不被时间窗口吞掉，再根据实际使用感受调阈值。

### P1 · 人格条件

我会选第三种：**按编辑动作分组，用时间判断连续打字是否该合并，而不是把两秒内的所有改动都合起来。**

逐字撤销太碎，删掉刚打的一小段要按很多次；纯时间窗口又太粗，用户刚打完字、马上粘贴，按一次撤销通常只想去掉粘贴内容，不想连前面的字也删掉。

可以先用这套规则：

| 操作                 | 撤销规则                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 普通打字             | 相邻两次输入间隔不超过 **750 毫秒**，且新文字紧接上一笔、期间没有主动移动光标或改变选区，就合并。超时或按回车就断组，回车单独记一条。 |
| 连续删除             | 同一方向、位置连续的退格或 Delete，可以按同样的时间阈值合并；不与打字合并。                                                           |
| 粘贴、剪切、替换选区 | 每次操作单独记一条。比如选中一段文字后粘贴，一次撤销就恢复原文。                                                                      |
| 移动光标、改变选区   | **结束当前分组，但本身不产生撤销记录。** 打字后光标自然前进不算主动移动。                                                             |
| 中文输入法           | 拼音、候选切换等未提交的预编辑不入栈；**一次提交记一条**，不与前后打字或其他提交合并。取消且没有提交就不记。                          |

比如，连续打出 `abc`，立刻粘贴一段文字，再移到行首用输入法提交「你好」。三次撤销应依次去掉「你好」、去掉粘贴内容、去掉 `abc`；光标移动不占一次。

**750 毫秒是可调的起点，不是语义规则。** 实现时按实际文本变更和操作来源分组，不要按 `keydown` 记账：一次按键未必改文档，一次粘贴或输入法提交也可能改多个字。

<details>
<summary>核对要点</summary>

处理交互边界，解释取舍。 连续相邻键入可合并，光标移动、粘贴、操作类型变化和较长停顿通常应断组。输入法的组合更新与最终提交应区分，避免把组合过程拆成用户撤销步骤。允许其他一致并可预测的分组。

</details>

## T-012

### 题面

后台每 5 分钟轮询一次导出任务，网络超时就再发一次创建请求。我倾向于直接重试，因为文件最多生成两次，似乎问题不大。可是客户端会把每个成功任务都显示在历史记录里。你会改客户端、服务端，还是先接受重复？

### A0 · 默认条件

我会**优先改服务端，让创建导出支持幂等；客户端配合复用同一个请求键**。如果服务端暂时改不了，我会先关掉创建请求超时后的自动重发，而不是在历史记录里隐藏重复项。

创建请求超时只说明客户端没收到响应，不说明服务端没创建任务。即使最多只重试一次、真的只生成两份文件，用户点一次导出却看到两条成功记录，也会搞不清哪条才是自己发起的。客户端按文件名或参数去重，又可能把用户主动发起的两次相同导出合并掉。

具体做法：

- **客户端**：每次用户主动发起导出时，先生成并保存一个请求键。创建超时后，用同一个键重试；用户主动再导出一次，才生成新键。拿到任务 ID 后，每 5 分钟只查状态，不再发创建请求。
- **服务端**：按“用户 + 请求键”做原子去重。同一个键、同一组参数，返回原任务 ID，即使任务还在运行；同一个键配不同参数则拒绝。这样历史记录里只有一条任务，而不是先创建两条再藏掉一条。

过渡期，创建超时就显示“提交结果未确认”，而不是“创建失败”。如果已有可靠的查询方式，就先查原任务；否则让用户知道再次提交可能产生重复。这比默认替用户再创建一次更稳妥。

### P1 · 人格条件

我会**优先在服务端把创建导出做成幂等，客户端配合；不在历史记录里按文件名或导出参数去重。**

关键不是多生成一次文件的成本，而是**创建请求超时不代表创建失败**。服务端可能已经建好了任务，只是客户端没收到任务 ID。此时重发一个没有幂等保护的创建请求，就会把用户的一次操作变成两条成功记录。客户端又无法仅凭参数判断：这是网络重试，还是用户确实想再导出一次？

- **客户端**：每次用户主动发起导出时生成并保存一个幂等键。创建超时后用同一个键重试；用户主动再导出一次，则用新键。拿到任务 ID 后，只重试状态查询，不再重发创建请求。
- **服务端**：用「用户 + 幂等键」做数据库唯一约束。同一个键、同一份参数的请求返回同一个任务 ID，即使两次请求同时到达；同一个键带了不同参数则拒绝。历史记录继续按任务展示，不用做额外推断。

如果服务端这期改不了，我会先**保留每 5 分钟的查询重试，但停掉创建超时后的自动重发**。如果能可靠查回原任务，就接着跟踪；否则提示「创建结果未确认，请先查看导出历史」，而不是直接标为失败。这样偶尔需要用户多看一眼，但不会由客户端自动制造重复任务。上线前最值得测的是：**服务端已创建任务、响应丢失，客户端重试后仍拿到原任务 ID，历史里只有一条记录。**

<details>
<summary>核对要点</summary>

识别超时的结果不确定性与重复成本。 超时不代表创建失败。可用稳定幂等键、归并已有任务或状态查询处理重试，并考虑并发重试以及重复历史。若首版接受重复，应明确代价及约束。

</details>

## T-013

### 题面

一个桌面聊天应用卡在“生成中”。日志里请求发出后收到 HTTP 200，随后几十秒都没有新的事件，界面上也没有文字。我同事说 200 证明模型已经生成完，问题肯定在界面。只凭这些线索，你会沿哪几步排查？每一步希望看到什么证据？

### A0 · 默认条件

**HTTP 200 不能证明模型已经生成完。** 对流式接口，服务端可以先发出 `200` 响应头，之后才开始生成正文。日志里“没有新事件”，也只说明那个日志点没记录到事件，不等于网络上没有收到数据。我会找的是：**同一个请求，在哪一层最后一次确认有进展？**

| 步骤                                    | 查什么                                                                                                             | 希望看到的证据                                                                                                                                                                                                         |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 确认 `200` 是在哪记的                | 对照客户端日志代码和接口契约，确认是收到响应头就记 `200`，还是读完整个响应才记；请求走的是流式还是普通 JSON。      | 同一请求 ID 下的状态码、`Content-Type`、收到响应头的时间，以及正文是否读完。流式接口的正常结束要看协议约定的结束事件或完成状态，不能只看 `200`。                                                                       |
| 2. 看客户端到底收到了什么               | 在事件解析**之前**观察响应体，把首个正文字节、首个有效内容事件和流结束分开记录。                                   | 几十秒内是**零字节**、只有心跳、收到了不完整的事件，还是已有完整内容？连接最后是正常结束、被重置，还是一直开着？这一步能区分“没收到内容”和“收到了但没解析出来”。                                                       |
| 3. 如果客户端没收到内容，沿链路往上查   | 用请求 ID 对齐服务端、网关和客户端日志，分别查上游何时开始生成、应用何时拿到首段内容并写出、网关何时向客户端转发。 | 上游没有首段内容，就查请求是否真正发到模型、是否排队或失败；上游有内容但应用没写出，就查服务端转发；应用已写出、网关却迟迟没转发，再查代理缓冲或压缩。必要时用相同配置做一次经网关和直连的对照，比较首段内容到达时间。 |
| 4. 如果客户端收到了内容，沿客户端往下查 | 依次验证：原始字节 → 解析出的事件 → 对应消息的状态更新 → 界面渲染。                                                | 有字节但无事件，查流格式、分帧和解析错误；有事件但消息状态没更新，查请求与消息 ID 的绑定、事件是否被丢弃；**消息状态里已有文本、画面仍空白**，才有证据把问题定位到渲染层。                                             |

另外，**“没出字”和“一直显示生成中”可能是两个问题**。即使根因在上游，也要单独确认：超时、断流、取消或缺少结束事件时，客户端有没有退出“生成中”并提示错误。

### P1 · 人格条件

我不同意同事的判断。**HTTP 200 只说明客户端收到了状态码为 200 的响应头，不证明响应体已经到达，更不证明模型已经生成完。** 对流式接口，服务端完全可能先发 `200`，几十秒后才发第一段内容。“没有新事件”也只说明当前日志点没记录到事件，不等于网络上没有字节。

我会用同一个请求 ID 串起下面几层，找出**最后一个有证据的节点**：

| 排查步骤                                              | 希望看到什么证据                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. 确认 200 之后，桌面端有没有读到响应体**          | 在网络读取层记录响应头到达时间、首个正文块的时间、累计字节数，以及连接是保持打开、正常结束还是报错。检查响应类型是否符合预期。关键是区分：**零正文、只有心跳、有内容**。如果客户端连正文都没读到，不能先归咎于渲染。                                                                                             |

### 题面

Windows 桌面应用偶尔保存完设置就读到空 JSON。日志里看到 `create(settings.json)` 成功，然后写入时报错，下一次启动解析失败。在掉电和同时有两个窗口保存的情况下，我想避免旧设置被清空。怎么改保存流程？还需要确认哪些假设？

### A0 · 默认条件

`create(settings.json)` 成功时，旧文件就已经被截断了；后续写入失败，留下的自然是空文件。**不要直接写正式文件。先在同目录写好、刷盘，再用 Windows 的文件替换 API 发布。** 两个窗口则要把整个“读—改—写”串行化，而不只是锁住最后一次替换。

### 建议的保存流程

1. **先加锁，再读当前设置。** 两个窗口在同一进程里，用一把共享 mutex；如果可能启动多个进程，用跨进程锁，例如锁一个不会被替换的 `settings.lock`。所有写入和恢复路径都要遵守同一把锁。把窗口实际改动的字段合并到刚读到的设置上。如果窗口提交的是打开时的整份快照，就带版本号检查冲突，否则加锁也挡不住后保存的窗口覆盖先前的改动。
2. **把完整 JSON 写到同目录的唯一临时文件。** Rust 里用 `create_new(true)` 创建，`write_all` 写完整；如果用了 `BufWriter`，先 `flush()`，再对底层文件调用 `sync_all()`，检查每一步的错误，然后关闭临时文件句柄。这一步失败就不发布，原 `settings.json` 不动。
3. **用一次替换操作发布。** 正式文件存在时可用 `ReplaceFileW`；确实是首次保存时，用同卷、不覆盖目标的重命名。不要用“先删除旧文件，再重命名”兜底。只有发布成功才报告保存成功；若替换调用报错，记录阶段和 Win32 错误码，重新检查文件状态，不要假定所有失败都原样保留了旧路径。
4. **保留一份验证过的旧设置。** 发布新版本前，可将已通过 JSON 解析和必要字段校验的旧版本，用同样的临时文件流程更新到 `settings.json.bak`。启动时优先读主文件；主文件确实缺失或内容损坏时，再尝试验证并读取备份。访问被拒绝、共享冲突等 I/O 错误不要当成损坏，更不要因此用默认值覆盖文件。

### 还要确认的假设

- **两个窗口保存的是什么？** 不同字段的改动通常应该合并；同一字段冲突是后保存者胜出，还是提示用户？还要确认是否有第二个进程或其他程序写同一份设置。
- **文件实际存在哪里、谁持有句柄？** 确认是本地 NTFS，还是网络盘、同步目录或重定向目录。检查自己的读取句柄是否允许删除共享（`FILE_SHARE_DELETE`）；遇到短暂共享冲突可以有限重试，但不要降级成原地覆盖。
- **“掉电安全”要求到哪一级？** 临时文件刷盘和替换解决的是“写到一半就破坏旧文件”。`sync_all()` 刷的是临时文件，不能据此保证替换后的目录项在突然断电后一定持久化；`ReplaceFileW` 的 `REPLACEFILE_WRITE_THROUGH` 标志也不受支持。要区分“重启后至少能恢复一份有效设置”和“已经提示保存成功的最新版绝不能丢”。如果后者是硬要求，建议评估 SQLite 事务及其同步配置，并在目标文件系统和硬件上实际验证。

测试时，至少注入**写入失败、刷盘失败、替换失败**，再让两个窗口基于同一旧版本分别改不同字段，验证两处改动都保留。强杀进程能验证应用崩溃恢复，但不能代替断电测试。

### P1 · 人格条件

把保存流程改成 **“先完整写入同目录的临时文件，再用替换操作提交”**。不要再对正式的 `settings.json` 调用 `create`：它一旦成功，旧文件就已经被截断，后续写入报错也无法把旧内容找回来。

### 建议的保存流程

1. **加锁，读取最新设置，再合并本次修改。** 同一进程的两个窗口共用一个 mutex，锁要覆盖整个「读 → 改 → 写 → 提交」，不能只锁最后的替换。窗口最好提交字段变更，而不是整份旧快照。例如 A 改主题、B 改字号，B 保存时应该在 A 已提交的版本上改字号。如果只能提交整份快照，就带上读取时的版本号，版本不匹配时拒绝或明确合并。同一字段的冲突也要定规则。
2. **把完整 JSON 写入同目录下唯一命名的临时文件。** 先在内存中序列化并检查，再 `write_all`；如果用了缓冲写入器，先 `flush`，再对文件 `sync_all`，最后关闭句柄。任何一步失败，都不要动正式文件。
3. **保留一份验证过的上一版本，再提交新版本。** 如果当前主文件能解析且通过应用的设置校验，就用同样的「临时文件 → 同步 → 替换」流程更新 `settings.json.bak`，不要直接截断备份。如果主文件已损坏，绝不能用它覆盖有效备份。随后用 Windows 的同卷替换操作提交新文件，例如 `MoveFileExW` 配 `MOVEFILE_REPLACE_EXISTING`，不启用跨卷复制；**不要先删正式文件再重命名**。如果选择 `ReplaceFileW`，要按其文档处理失败后各文件的状态，不能一概假设“报错就等于没改动”。
4. **启动时先验证主文件，再尝试备份。** 主文件为空、损坏或缺失时，可以从有效备份恢复，并记录发生了回退。区分内容损坏和权限、共享冲突等读取错误；不要把暂时读不到当成首次启动，更不要因此自动用默认值覆盖。残留的临时文件也不要默认当成已提交版本。

### 还需要确认的假设

| 确认项                                                     | 为什么重要                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 两个窗口一定在同一进程吗？                                 | 如果能开多个实例，进程内 mutex 不够。用所有写入者都遵守的跨进程锁，例如命名 mutex，或锁一个不会被替换的独立锁文件。拿到锁后再读最新版本。                                                                                                                                  |

### 题面

我想证明对所有正数 a、b，有 (a+b)(1/a+1/b)≥4。我写到 a/b+b/a≥2，说这是因为 a/b≥1 且 b/a≥1，好像不对。能指出错在哪里，给一个完整证明并写出等号条件吗？

### A0 · 默认条件

错在于 \(\frac ab\) 和 \(\frac ba\) 互为倒数：如果 \(a>b\)，那么 \(\frac ab>1\)，但 \(\frac ba<1\)；如果 \(a<b\)，则恰好相反。只有 \(a=b\) 时，它们才都不小于 \(1\)。

不过，你要证明的 \(\frac ab+\frac ba\ge 2\) 是对的。因为 \(a,b>0\)，所以
\[
\frac ab+\frac ba-2
=\frac{a^2+b^2-2ab}{ab}
=\frac{(a-b)^2}{ab}\ge 0.
\]
因此
\[
(a+b)\left(\frac1a+\frac1b\right)
=2+\frac ab+\frac ba\ge 4.
\]

**等号成立当且仅当 \(a=b\)**，因为这恰好是 \((a-b)^2=0\) 的条件。

### P1 · 人格条件

错在把 \(\frac ab\ge 1\) 和 \(\frac ba\ge 1\) 当成同时成立。前者等价于 \(a\ge b\)，后者等价于 \(b\ge a\)。如果 \(a\ne b\)，这两个比值一个大于 \(1\)，另一个小于 \(1\)。

你的展开思路是对的。因为 \(a,b>0\)，所以
\[
\begin{aligned}
(a+b)\left(\frac1a+\frac1b\right)-4
&=\frac ab+\frac ba-2\\
&=\frac{a^2+b^2-2ab}{ab}\\
&=\frac{(a-b)^2}{ab}\ge 0.
\end{aligned}
\]
因此 \((a+b)(1/a+1/b)\ge 4\)。

**等号当且仅当 \(a=b\) 时成立**，因为分母 \(ab>0\)，而分子 \((a-b)^2\) 恰好在 \(a=b\) 时为零。

<details>
<summary>核对要点</summary>

指出推理错误并完整证明。 当 a、b 不相等时 a/b 与 b/a 中一个小于 1。展开得 2+a/b+b/a，且差值 (a−b)²/(ab) 非负。可用等价的 AM–GM 证明。等号当且仅当 a=b。

</details>

## T-020

### 题面

掷两个可以区分的公平六面骰。已知至少有一枚是 6，两枚点数之和至少是 10 的概率是多少？我算成 1/2，因为另一枚只要是 4、5 或 6。这个推理错在哪里，还是答案其实对的？

### A0 · 默认条件

答案是 **\(5/11\)**，不是 \(1/2\)。你说“另一枚只要是 4、5 或 6”没错；问题在于，**“至少有一枚是 6”不等于“指定的那一枚是 6”**。

两个骰子可以区分。满足“至少有一枚是 6”的等可能结果有 \(6+6-1=11\) 个：第一枚是 6 的有 6 个，第二枚是 6 的也有 6 个，但 \((6,6)\) 被数了两次。

其中，点数和至少是 10 的有 5 个：
\[
(6,4),\ (6,5),\ (6,6),\ (4,6),\ (5,6).
\]
所以概率是 \(\boxed{5/11}\)。

如果题目说的是“**第一枚**骰子是 6”，那么第二枚的六个点数仍然等可能，你算的 \(3/6=1/2\) 就是对的。

### P1 · 人格条件

答案是 **\(5/11\)**。你判断“另一枚必须是 4、5 或 6”没错；错在把“至少有一枚是 6”当成了“指定的那枚骰子是 6”。只有后一种情况下，另一枚骰子的六种点数才仍然等概率。

按顺序记两枚骰子的点数。第一枚是 6 有 6 种结果，第二枚是 6 也有 6 种，但 \((6,6)\) 在两边都算到了，所以符合已知条件的等概率结果一共有 \(6+6-1=11\) 种。

<details>

正确处理条件样本空间。 至少一枚为 6 时有 11 个等可能有序结果，和至少为 10 的有 (6,4)、(4,6)、(6,5)、(5,6)、(6,6) 五个，概率 5/11。预先指定某一枚为 6 才对应均匀的另一枚。

## T-021

### 题面

一排 10 盏灯最初都是灭的。一次操作必须同时翻转相邻两盏灯的状态，每盏灯只在这排里和左、右相邻的灯相邻。任意指定两盏灯，能做到最后仅它们亮吗？如果只指定一盏呢？我想要一个能用于任意位置的论证。

### A0 · 默认条件

**任意指定两盏灯，都能做到最后只有它们亮；只指定一盏则做不到。**

把灯从左到右编号为 \(1\) 到 \(10\)。假设指定的是第 \(i\) 盏和第 \(j\) 盏，其中 \(i<j\)。依次翻转相邻的灯对
\[
(i,i+1),\ (i+1,i+2),\ \ldots,\ (j-1,j)。
\]
两端的第 \(i\) 盏和第 \(j\) 盏各翻转一次，所以变亮；中间每盏灯都翻转两次，所以仍然是灭的；区间外的灯从未被翻转。这个做法适用于任意两个位置，包括两盏灯本来就相邻的情况。

只亮一盏则不可能：每次操作使亮灯总数增加 \(2\)、减少 \(2\) 或保持不变，所以亮灯总数的奇偶性不变。最初亮灯数是 \(0\)，因此最后也只能有偶数盏灯亮。

### P1 · 人格条件

**任意指定两盏灯，都能做到最后只有它们亮；只指定一盏则不可能。**

把灯从左到右编号为 \(1\) 到 \(10\)。如果指定的是第 \(i\) 盏和第 \(j\) 盏（\(i<j\)），就沿着它们之间的区间，依次翻转
\[
(i,i+1),\ (i+1,i+2),\ \ldots,\ (j-1,j)。
\]
两端各被翻转一次，所以亮；中间每盏都被翻转两次，所以回到灭；区间外的灯没被翻转，仍然灭。这个方法适用于任意两个位置，包括两盏灯紧挨着的情况。

只亮一盏不可能，因为每次操作让亮灯数增加 \(2\)、减少 \(2\) 或保持不变，所以**亮灯数的奇偶性始终不变**。最初亮灯数是 \(0\)，最后就不可能是 \(1\)。

<details>
<summary>核对要点</summary>

构造与不变量都完整。 沿任意两个指定位置之间的每条邻接边各翻转一次，内部灯翻两次，端点翻一次。亮灯总数的奇偶性保持偶数，单盏不可达。

</details>

## T-022

### 题面

一所学校在自愿参加的学生中试用新的阅读工具。用了一个月的学生平均提高 8 分，没有用的学生平均提高 3 分。两组按年级分布差不多。我想在报告里写“工具使学生多提高了 5 分”。目前能写到什么程度？下一轮怎么设计才更能回答因果问题？

### A0 · 默认条件

**目前可以写“使用组平均多提高了 5 分”，但不能写“工具使学生多提高了 5 分”。** 前者是观察到的组间差异，后者是因果结论。

报告里可以这样写：

> 在为期一个月的试用中，使用阅读工具的学生平均提高了 8 分，未使用的学生平均提高了 3 分，两组平均增分相差 5 分。两组的年级分布相近，但由于没有随机分配，这一差异不能归因于工具本身。

年级分布相近，只说明两组在年级构成上差不多。使用工具的学生可能本来就更有学习动力，也可能在起始阅读水平、额外练习时间或教师支持上不同。如果有样本量和个体成绩，可以给这 5 分附上置信区间，说明估计有多精确；但区间再窄，也不能排除自我选择带来的偏差。

**下一轮最有用的改动是：先招募并做前测，再随机分配。**

1. **在各年级内随机分组。** 把同意参加的学生随机分到“立即使用工具”组和“一个月后再使用”组。如果同班学生很容易共享工具，或教师很难在同一班内实施两种安排，可以按班随机，并在样本量规划和分析中考虑同班学生成绩的相关性。
2. **让对照组对应你真正想问的问题。** 如果想知道“学校引入工具后，是否比照常教学更好”，对照组照常学习即可。如果想知道“同样多练一个月，用这个工具是否比普通阅读练习更好”，两组就应安排相同的练习时间。两组在同一时间用同样的方式测评。
3. **按原随机分组分析，不按实际使用情况重新分组。** 即使有些分到工具组的学生没怎么用，也保留在原组。事先定好主要阅读指标，用前测成绩做调整来比较一个月后的成绩，并报告组间差值、置信区间、实际使用情况和各组缺测人数。

这样能更可信地回答：**对愿意参加的学生，分配使用这个工具一个月，比所选的对照安排带来多少变化？** 结果不自动代表全校学生，也不说明效果能维持多久。

### P1 · 人格条件

**可以写“使用组平均多提高了 5 分”，但目前不能写“工具使学生多提高了 5 分”。** 前一句描述观察到的组间差异，后一句把差异归因于工具。

报告里可以这样写：

> 一个月后，使用阅读工具的学生平均提高 8 分，未使用的学生平均提高 3 分，两组平均增分相差 5 分。由于学生并非随机分组，这一差异不能直接归因于工具。

两组年级分布相近，只说明它们在年级这一项上相近。即使都来自自愿参加的学生，实际使用工具的人也可能在起始阅读水平、学习动机或额外练习时间上不同。比较的是“增分”，也不能自动消除这些差异。报告最好同时列出两组人数、起始分数和缺测情况；如果有个体数据，可以给出 5 分差异的置信区间，但区间反映的是估计精度，不能消除自选偏差。

**下一轮，最值得改的是：先招募、做前测，再随机决定谁先用。**

1. **在同一批志愿学生中随机分组。** 可按年级和前测水平分层，一组立即使用，另一组维持常规阅读、一个月后再获得工具。如果同班学生很容易共享工具或互相影响，可以按班随机，但样本量和分析都要考虑班级聚集。
2. **让对照组对应你真正想回答的问题。** 如果想知道“在常规教学上加这个工具有没有帮助”，候补组就合适。如果想知道“同样多练一个月，用这个工具是否更好”，对照组也应安排等时的常规阅读练习。两组在同一时间、用同等条件测评，评分者最好不知道分组。
3. **事先定好主要结果，按原随机分组分析。** 例如，比较一个月后的阅读分数，并用前测分数作调整；报告组间差异和 95% 置信区间。即使有学生没按安排使用，也不要在主分析里把他们换组或剔除；尽量收齐两组后测，另行报告实际使用和缺测情况。

这样，下一轮就能更有把握地回答：**在这批自愿参加的学生中，安排使用工具一个月，相比指定的对照安排，平均带来了多少变化。** 这仍不等于工具对全校学生都有同样的效果。

<summary>核对要点</summary>

分辨选择偏差与因果，给出可执行设计。 可以描述样本内 5 分的观察差，年级相似不能消除基线、动机及其它混杂。推荐预先定义指标、控制基线并随机分配或采用有说明的替代设计。

</details>

## T-023

### 题面

我们测某种新涂层的耐磨性。第一批样品里处理组明显更耐磨，第二批的差异接近零。第一批所有对照在上午测、处理在下午测，第二批把两组交替测。两批原料标称相同。下一轮资源只够做一批，怎样安排才能区分涂层效应和测量顺序效应？

### A0 · 默认条件

**下一轮用同一批原料，把处理组和对照组分散到上午和下午，并在每个时段内平衡谁先测。** 第一批里，“有无涂层”和“上午还是下午”完全重合，无法判断差异来自哪一个；第二批差异接近零，也不等于涂层没有效应。

可以这样排：

1. **先配对，再随机分组。** 从同一批原料中，把相邻位置或初始状态相近的两件试样配成一对，随机选一件做涂层，另一件做对照。每件用独立试样，不把同一件的重复读数当成独立样本。
2. **每个时段都安排两种顺序。** 例如有 8 对，上午和下午各测 4 对；每个时段各有 2 对“处理→对照”和 2 对“对照→处理”，随机打乱这 4 对的测试顺序。每对尽量紧挨着测。这样两组既共享早晚条件，也不会总是同一组先测。
3. **记录实际时间和测量序号。** 按统一规程清洁夹具、检查磨料和仪器状态；如果怀疑仪器随测试进程漂移，可在开头、中间和结尾插测标准参考样。

分析时，先算每对的“处理－对照”耐磨差，报告平均差和置信区间；再按**上午／下午**和**处理先测／后测**分别看这个差值。若两种顺序下差值接近、方向一致，更支持涂层效应；若差值随先后明显变化甚至反号，就要警惕顺序效应。也可以比较**同一组**上午和下午的读数，检查两组是否出现共同漂移——这种漂移即使不改变配对差，也可能解释第一批的表观优势。

这一轮能把**本批的涂层效应**与测试安排分开，但只有一批，仍不能判断涂层效果是否因原料批次而异。

### P1 · 人格条件

下一轮用**同一批原料，随机分配涂层处理，并在每个时段内平衡两组的测试顺序**。关键不是简单地交替测，而是让对照和涂层样品都覆盖上午、下午，而且两组都有机会先测和后测。这样，即使仪器读数随时间漂移，也不会系统性地偏向某一组。

**具体排法：**

1. **先配对，再随机分组。** 尽量把来自同一原料位置、初始状态相近的两件试样配成一对，随机决定哪件做涂层、哪件做对照；除涂层外，其余制备和测量条件尽量一致。
2. **每两对组成一个四件测试区组。** 一对先测对照、另一对先测涂层，随机决定哪一对先上机。这样每个区组的顺序是「对照–涂层–涂层–对照」或反过来。把区组分布在上午和下午，尽量覆盖第一批原来的测试时段。不要固定成每一对都由对照先测。
3. **记录实际时间和上机序号。** 如果资源允许，在开头、中段和末尾测稳定的参考样，帮助判断仪器是否漂移。如果上一件试样可能改变磨头状态或留下残留，就按统一规程清洁、复位或更换耗材，别指望随机化消除这种影响。

**分析时，先算每对的「涂层 − 对照」差值**，报告平均差和置信区间，再看上午和下午的配对差是否一致。同时看两组的读数是否随时段或序号一起变化：如果两组一起漂移，但配对差稳定，说明顺序相关漂移和涂层效应可以同时存在；如果两组一起漂移，而配对差接近零、且区间足够窄，能排除有实际意义的改善，那就更支持第一批的表观优势来自测量安排。若配对差本身随时段变化，就分时段报告，不要只看总平均。

这一轮能把**本批的涂层效应**和**本轮的顺序相关变化**分开估计，但不能回头精确拆解第一批的结果，也不能用一批样品排除批间差异。

<details>
<summary>核对要点</summary>

在资源约束下检验两个解释。 同一批内在各时间段都随机或分块均衡安排两组，控制测量环境并记录顺序，可盲化操作者。说明第一批组别与时间混杂，第二批的零差异也只反映有限证据。

</details>
