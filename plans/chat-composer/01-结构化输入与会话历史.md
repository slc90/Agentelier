# 建立结构化输入与会话历史

设计依据：[相关设计文档](../../docs/design/modules/chat-composer.md)。

## 目标

让一条用户消息能够同时保存文本段、能力引用、文件引用和多个媒体附件的身份，并在发送、排队、重试和历史恢复时保留同一份消息内容。此阶段建立数据契约与持久化边界，不实现新的 Composer UI。

## 当前输入为什么需要统一

现有 `ConversationRequest::Send` 以 `input: String` 为主，并另外携带一个可选 `AudioId` 和转写引用；`CreateAndSend` 只接收字符串。会话视图也只有一个 `audio_draft`。队列输入以文本和转写引用为主，Turn 历史主要保存文本与单个音频引用。

这套表示无法描述多张图片、多个音频、Skill/MCP 引用和文件路径在同一条消息中的关系。继续增加 `image: Option<_>`、`audio: Option<_>` 之类的平行字段，会让每种新媒体都要求修改 Send、Queue、Retry 和历史模型。

本阶段引入一个统一的结构化输入快照。它保存逻辑内容与稳定引用，不把媒体字节放进 Bridge 事件或 UI 资源。

## 结构化消息快照

消息快照按顺序保存内容元素。元素至少区分：

- 文本段：保留用户输入的实际文字。
- Skill 引用：保存 Skill 的稳定来源身份，不只保存显示名称。
- MCP 引用：保存 Server 或 Tool 的稳定身份。
- 文件引用：保存相对于当前会话工作目录的路径。
- 图片附件引用：保存会话内不可变附件 ID。
- 音频附件引用：保存会话内不可变附件 ID。

每个元素具有稳定 ID。媒体元素还关联 MIME、文件名、摘要和大小等安全元数据。文本段可以相邻合并，但引用和媒体元素的相对顺序不能改变。

草稿是可变状态；提交快照是不可变状态。Conversation 接纳一条消息后，后续编辑不得改变已经接纳的内容。Session Store 负责保存媒体字节，消息只保存附件 ID 和摘要。这样 Retry 与历史恢复不会重新读取最初选择的临时文件路径。

提交快照同时保留已有的可选 `TranscriptReference`。其关联的会话、附件和文稿版本继续作为独立请求材料恢复。存在多段音频时，文稿引用仍明确指向原来选中的版本。

## 首条消息随会话提交

选择文件时由 Session Store 校验并保存草稿暂存快照，Bridge 向 Composer 返回暂存引用和显示元数据。新会话草稿使用自己的暂存归属。发送时 Runtime 冻结草稿修订及会话设置，Conversation 准备首条 `Accepted`。

Session Store 先将已选附件写入正式会话附件目录并校验引用，再将 `Created` 和首条 `Accepted` 写入同一份临时日志并一并发布。日志发布是会话可见和首条消息接纳的共同边界。收到回执后登记会话、清理对应草稿修订并启动模型请求。首条消息沿用已提交的 `Accepted`，模型启动只消费这次回执。

发布前失败清理本次尚未发布的会话文件，草稿与暂存快照可以继续编辑和重试。重启时按已发布日志区分正式会话和待回收的半成品。回执不明确时按首条提交的稳定身份核对日志。确认已发布后继续原会话，模型失败时从正式附件重试。

## 输入生命周期使用同一契约

结构化快照需要覆盖以下输入入口：

- `Send`：当前会话开始一个普通用户 Turn。
- `CreateAndSend`：创建会话并提交第一条结构化消息。
- `Queue`：接纳时提交完整快照和正式附件引用，出队后作为新 Turn 处理并重新校验能力。队列取消时释放自己的引用，存储层保留其他草稿、在途提交或历史仍引用的附件。
- `Retry`：读取原 Turn 已保存的结构化消息和附件身份。
- `ContinueWithoutCompaction`：沿用失败请求对应的冻结输入，不重新读取 UI 草稿。

Steer 保持现有文本输入语义。现有 Skills 规则明确要求带显式 Skill 选择的输入经 Queue 或新任务边界处理，因此富输入不能在 Steer 路径中被压成文本。活动 Turn 中带 Skill/MCP 引用或媒体的草稿应进入 Queue，或等待当前 Turn 结束后再发送。

消息接纳回执仍是清除草稿的边界。发送期间用户继续编辑时，新内容属于下一份草稿修订；旧请求的接纳回执只清除自己提交的快照。

## Conversation、Bridge 与 Session Store 的职责

Conversation 负责验证消息元素之间的关联，并决定何时接纳输入。Bridge 只传递结构化快照和附件身份，不传输大型 Base64 内容。Session Store 保存不可变图片与音频附件，并在消息接纳前返回可核对的附件 ID。

TurnView、QueuedInput 及历史投影表达结构化消息，SteerView 沿用纯文本。旧存档的字符串用户输入按纯文本恢复，已有单音频恢复为一项音频附件，已有文稿引用恢复其原始版本。旧 JSONL 记录原样读取。

图片输入附件与工具生成图片是不同来源。两者可以共享底层内容寻址存储能力，但消息方向、用途、历史关联和可见呈现必须分开。音频附件继续使用现有 Session Store 的摘要和不可变文件机制，数据模型扩展为多项引用。

## 完成条件

- 一条消息可以包含多个文本段、多个引用和多个媒体附件。
- Send 与 CreateAndSend 使用相同的结构化输入契约。
- Queue 保存完整输入快照，出队后不丢失媒体或引用。
- Retry 与 ContinueWithoutCompaction 重放原始结构化输入，不重新读取用户原始路径。
- 旧纯文本历史和现有单音频历史仍能正常读取。
- 直接发送、排队、重试和恢复都保留已选择的转写文稿版本。
- 接纳失败时附件和草稿仍保留；接纳成功后历史只引用已提交附件。
- 新会话和首条富媒体消息一并可见。首条提交只产生一个可恢复会话和一条接纳记录。
- Bridge 事件不携带图片或音频的完整二进制数据。

## 验证

沿现有会话生命周期验证纯文本 Send、CreateAndSend、Queue、Retry 和恢复流程。使用现有单音频与已保存文稿检查接纳、队列取消和恢复。核对首条接纳确认后只出现一条消息，存储拒绝时草稿仍可编辑。图片与音频的多附件 GUI 场景分别在第 06、07 步验收。按项目现有规则进行编译和运行验证。
