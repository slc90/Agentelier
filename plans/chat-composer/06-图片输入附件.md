# 接入图片输入附件

设计依据：[相关设计文档](../../docs/design/mechanisms/codex-input-submission.md)。

## 目标

让用户能够把本地图片加入 Composer，并通过 Codex `LocalImage` / `Image` 输入路径发送给支持图片输入的模型。图片在 Composer 中按用户插入顺序显示，模型请求按 Codex CLI 的图片分组规则组织。

## 输入与持久化

图片可通过文件选择入口添加。本步接入第 05 步的 `@` 选择结果，将图片候选交给附件暂存并创建图片元素。Session Store 保存经过校验的草稿快照，消息接纳时绑定为正式附件。记录包含 MIME、大小、尺寸、摘要、原始文件名和会话身份。

用户输入图片与工具生成图片分开保存和投影。当前 `ImageAttachmentAction` 服务于工具生成图片预览/导出，不作为用户图片上传或消息附件的唯一身份。

Bridge 传递暂存引用、正式附件 ID 和显示元数据。Session Store 负责受控读取。首条会话消息沿第 01 步一并提交正式附件与接纳日志。已接纳消息的 Retry 和历史恢复继续使用正式附件。

## Codex 提交

本地图片沿 Codex `LocalImage` 路径处理，使用现有图片预处理和 MIME 识别规则，最终生成 `input_image` 内容项。多个图片按附件顺序编号，图片载荷按 Codex TUI 的类别顺序放在完整文本之前，文本保留对应 `[Image #n]` 占位符和文本元素映射。

图片在 Composer 中可以出现在文字中间或开头；这一视觉顺序不改变最终请求的图片分组方式。选择普通 `@` 文件时仍然只插入路径文本，只有图片文件进入本流程。

## 模型能力

图片可先添加和预览。提交前使用现有 `image_input` 字段判断模型是否明确支持图片。能力未知或明确不支持时区分提示，保留附件和草稿。

图片输入继续使用 Codex 的图片大小与处理预算，不另造一套任意图片上传协议。图片内容进入模型请求前必须完成实际格式识别和预处理，失败时保留原附件并报告原因。

## 完成条件

- 可在同一消息中添加多张图片。
- 图片附件按插入顺序在 Composer 中显示，且不与工具生成图片混淆。
- `@` 选择图片时创建图片附件元素；选择普通文件时仍插入路径文本。
- 发送时生成 Codex `input_image`，图片编号与文本占位符对应。
- 只允许明确支持图片输入的模型发送图片。
- Retry 和历史恢复使用已保存的不可变图片附件。
- 已进入模型工作窗口的图片沿第 02 步契约参与估算、重放和压缩。

## 验证

通过 BRP 从文件选择器和 `@` 添加多张图片，检查文本前、中、后的显示顺序。验证新会话首条图片消息、已有会话 Send 和 Queue，核对重新打开及 Retry 使用同一份附件。检查真实模型请求中图片类别先于完整文本，编号与占位符一致。验证无法解码、超限、图片能力未知和明确不支持时保留草稿并返回对应错误。
