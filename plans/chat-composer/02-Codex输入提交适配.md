# 建立 Codex 输入提交适配

设计依据：[相关设计文档](../../docs/design/mechanisms/codex-input-submission.md)。

## 目标

建立结构化消息到 Codex 用户消息的转换，并定义文本、引用和图片在请求历史中的重放。认证、模型来源、工具调用和 Responses 路由沿现有通信路径。音频直传的请求实现和端到端验收归第 07 步。

## 输入适配器的职责

提交适配器位于 Conversation 与 LLM Model 之间。它接收已接纳的结构化消息和会话内附件引用，生成一条完整的 Codex 用户消息。它不读取 UI 状态，不自行搜索文件，也不在发送时重新发现 Skill 或 MCP。

Codex 的 `UserInput` 已经区分 Text、Image、LocalImage、Audio、LocalAudio、Skill 和 Mention。Agentelier 应沿用这些输入类型的职责划分，并在自己的请求模型中保留等价语义。

## 按 Codex CLI 的类别组织输入

对图片、文本和 Skill/Mention，遵循 Codex TUI 的现有 `input_submission.rs` 组织顺序：

1. 远程图片附件。
2. 本地图片附件。
3. 完整文本内容。
4. Skill 结构化引用。
5. Codex 支持的 Plugin/App Mention。

Agentelier 的用户图片使用本地附件，因此主要落在本地图片类别。文本内容保留图片占位符，路径引用仍位于文本原位置。图片载荷先于完整文本提交，不把每段文字拆成独立 user message。

保留结构化快照中的音频附件身份。第 07 步实测直传可用后，才启用把音频放在完整文本之后的序列化规则。用户选择的已有转写继续沿独立材料流程发送。

MCP 引用由 Agentelier Runtime 对照会话冻结的 ToolCatalog 和实时连接状态解析，作为本地工具上下文传递。

## 模型请求使用内容数组

当前 `ProtocolItem::User(String)` 只能重放纯文本。它需要升级为结构化用户消息，模型请求中的 `content` 使用有序内容数组：

- 普通文字转换为 `input_text`。
- 图片转换为 `input_image`，并使用 Codex 的本地图片标签/占位符机制。
- Skill 和 Mention 在本地请求准备阶段解析。仅对手写文本应用现有 `$name` 规则，已绑定的引用按身份解析。
- `@` 普通文件路径保留在 `input_text` 中。
- MCP 结构化身份由 Agentelier 的工具上下文解析，模型仍通过既有 Function Tool 声明调用 MCP。

一条 Composer 消息最终仍对应一条用户消息。不要为每个文字段或媒体附件创建独立的 Responses user message。

## 模型能力来自目录元数据

当前目录由 `input_modalities` 解析 `ModelInfo.image_input`。用户图片在发送时要求明确支持，未知与明确不支持分别提示，并保留草稿和附件。工具输出的图片沿用当前规则。音频直传的能力投影与传输校验在第 07 步落实。

## 历史、重试与请求冻结

`ProtocolHistory` 保存完整的结构化用户消息和附件引用。请求准备时生成冻结的内容数组与字节，认证恢复复用同一份请求内容。Retry 从会话历史恢复已保存附件，不重新读取原始用户路径，也不根据当前 Skill 目录或 MCP 连接状态重建原引用。

更新协议存档、重放校验、上下文估算和压缩契约。工作窗口中的用户图片计入模型上下文估算，重放时读取正式附件。压缩可以移出已处理的工作历史，聊天历史仍能展示原附件。直传音频的计量在第 07 步结合真实请求落实。

请求投影需要记录媒体类别、附件 ID、MIME、大小、摘要、图片/音频编号和结构化引用身份。日志与诊断不能记录完整 Base64、Token、认证头或完整用户音频内容。

## 完成条件

- 纯文本请求按 Codex Responses 的 `content[]` 形式生成，现有文本语义不变。
- 多张图片按 Codex TUI 类别顺序进入同一条用户消息，文本中的图片占位符与载荷编号一致。
- Skill 引用由现有 Skills 机制处理；MCP 引用由现有 ToolCatalog 处理，不增加自定义 Responses 内容类型。
- 用户图片参与工作窗口的估算、重放和压缩，已保存转写文稿保持原有的独立材料语义。
- Retry、认证恢复和继续执行使用冻结的原始输入，不重新读取外部路径。
- 请求错误保留真实错误，不静默丢弃不支持的附件。

## 验证

使用现有应用验证纯文本和已保存文稿请求。检查请求准备与存档投影中的用户消息、内容数组、编号和附件估算契约。真实图片附件的导入与送模在第 06 步一并验证，直传音频与显式转写在第 07 步按实际能力验证。
