# 接入音频文件输入

设计依据：[相关设计文档](../../docs/design/mechanisms/codex-input-submission.md)。

## 目标

让用户能够在同一条消息中添加多段音频，并复用主线的附件展示、播放与波形。原始音频直传由本阶段的真实请求结果决定。直传确认不可用时，交付现有的附件保存、显式转写和文稿问答路径。

## 验证现有 Codex 路径

本阶段先用 Agentelier 现有 Codex OAuth、目标模型和实际 Responses 请求传输，发送带 `input_audio` 的短音频。记录模型、传输、目录能力和实际终态，核对完整响应及其与音频内容的对应关系。HTTP 和 WebSocket 按适用路径分别验证，只有已确认可用的组合启用直传。暂时的连接或授权失败沿现有错误处理，待得到明确能力结果。

## 两种方式共用正式附件

添加时在 Session Store 保存不可变的草稿快照。消息接纳时建立正式附件引用，首条消息沿第 01 步与会话一并提交。原件保留 MIME、文件名、摘要、时长和字节数，播放、转写、恢复和 Retry 都基于已保存的快照。

### 直传确认不可用时

沿用常规附件路径，将 WAV 或 MP3 随消息绑定并保留播放。用户选择转写时，由现有 `/backend-api/transcribe` 请求读取正式附件。用户可以选择已保存的文稿版本，通过 `TranscriptReference` 继续问答。界面显示所用文稿版本。转写保留现有格式和 20 MiB 单文件规则。

### 直传可用时

从目录的 `input_modalities` 解析 `audio_input`，经 Model、Bridge 和会话设置提供给 Composer。启用直传需要目录明确声明 `audio`，并确认该模型在实际传输中可用。能力未知或不匹配时保留附件并提示可用的处理方式。

Codex `audio_mime_for_path()` 支持 WAV、MP3、M4A、WebM 和 OGG。Agentelier 额外接受 FLAC，但 FLAC 不直接传给 Codex：提交前无损解码并转换为 WAV，使用 `audio/wav`。

| 原始格式 | 模型提交方式 |
|---|---|
| WAV | 原格式提交 |
| MP3 | 原格式提交 |
| M4A | 原格式提交 |
| WebM | 原格式提交 |
| OGG | 原格式提交 |
| FLAC | 转换为 WAV 后提交 |

FLAC 的 WAV 转换结果只用作请求载荷，原件继续用于播放和恢复。输入原件与转换后的 WAV 都接受大小检查，超出 50 MiB 时提示并保留原件。

直传的 50 MiB 单文件约束覆盖导入、描述校验、写入、读取和请求准备。按实测内容形态补齐工作窗口的音频估算、重放和压缩，与转写的容量和格式规则独立。

每段直传音频在完整文本之后进入同一条用户消息。请求适配器按稳定顺序分配编号，保证前置标记、`input_audio`、结束标记与文本中的 `[Audio #n]` 对应。上游 `Audio` 形态直接产生载荷，这种情况下由适配器补齐标记。Retry 使用正式附件和保存的转换规则。请求内的认证恢复复用冻结字节。

## 现有音频控件的复用边界

草稿通过暂存引用读取音频，历史通过会话附件 ID 读取。两个入口共用当前播放、暂停操作和波形反馈。暂停后从原位置继续，播放结束后从头重播，开始另一段音频时停止并重置前一段。

直传可用时，为新接收的格式扩展现有解码路径或提供预览副本，新格式仍使用相同控件。模型提交使用上表所列格式和 MIME。

## 完成条件

- 一条消息可以包含多个音频附件。
- 草稿和历史复用现有音频附件播放和波形控件。
- 多段音频播放时一次只播放一段；开始新音频会重置之前的音频。
- Retry 与历史恢复使用正式附件。需要重建直传载荷时使用已保存的转换规则。
- 确认直传不可用时，普通消息可以绑定音频，用户可播放原件、显式转写并选择文稿。
- 直传可用时，完成已验证模型和传输的 `input_audio`、规定格式、编号标记、单文件校验和历史重放。

## 验证

通过 BRP 添加多段音频，检查显示顺序、播放与暂停、重播、切换，以及首条消息接纳后重新打开会话。验证转写由用户发起，选中的正式文稿进入请求材料。若启用直传，验证各格式、FLAC 转换前后的大小检查、模型能力不匹配、实际请求中的 `input_audio`、MIME、编号和历史重放。
