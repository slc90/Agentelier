# 在压缩后的工作窗口恢复当前项目规则

本增量解决一个独立问题：项目规则进入协议历史后，服务端压缩可能移走其明文。文件没有变化，也不能据此认定新的工作窗口已经包含可直接阅读的完整规则。

依赖[动态发布](03-refresh-project-instructions.md)已有的快照、替换／移除通知和持久记录，在它们之上加入窗口级发布状态。后续[请求核对界面](05-inspect-request-instructions.md)使用这里保留的窗口与重新发布事实展示实际材料。设计依据见[压缩与计量](../../docs/design/project-instructions/03-lifecycle-and-compaction.md)。

```mermaid
flowchart LR
    H["旧历史：项目发布、对话、工具"] --> C["Inline compaction 响应"]
    C --> S["工具结果封闭，检查点持久确认"]
    S --> W["安装新工作窗口"]
    W --> F["标记需要明确发布项目状态"]
    P["历史窗口之外保存的完整项目快照"] --> F
    F --> R["下一请求重新采集并追加当前全文或清除"]
```

## 项目快照与窗口内的发布不是同一个状态

最近成功的项目快照继续保存完整来源、作用目录、正文和确定性摘要，不随活跃历史裁剪而消失。它说明客户端掌握的规则；窗口内发布记录说明模型在这个工作窗口中是否已经得到明确的当前项目状态。

因此，决定是否追加项目项不能只比较文件摘要。需要同时检查窗口身份，以及在该窗口中已确认的发布记录。文件不变而窗口刚安装，应重新发布；文件和窗口均未变，则继续复用。

不要求解读 compaction 的不透明正文来判断某条工程规则是否“应该还记得”。明文恢复使用已保存的规则及下一请求的新采集结果，不能把摘要器可能保留的语义当作完整原文。

## 接在已有的封闭检查点之后

继续使用现有服务端 Inline compaction。完整响应仍先保存，所有函数调用结果仍先封闭，然后准备并持久提交检查点，确认后才安装新的工作历史、窗口身份与计量状态。本步不增加独立压缩请求、configuration_update、手工摘要或新的模型会话协议。

成功安装检查点时，把项目状态标记为“本窗口尚未明确发布”。这项状态与检查点恢复语义一起保存；不能只更新内存，否则应用在下一请求之前退出后，会丢掉重新发布的需要。

保留 compaction 项及其后助手、reasoning、工具调用和结果的原始顺序。项目重新发布追加在下一请求的可追加尾部，不插进未封闭调用和结果之间，不将原始密文改写为文本说明，也不为了把项目项放在窗口最前面重排已有项。

检查点保存失败或确认不确定时，沿原有阻断规则停止续接，不提前切换窗口、不提前清除发布状态。恢复时应服从已确认的检查点，不能被后面的异常展示记录重新覆盖成旧工作历史。

## 下一次请求只发布一份最新状态

下一逻辑请求仍经过普通的项目发现与有界读取。成功采集后，根据当前内容和新窗口条件生成一条更新：

| 新窗口的采集结果 | 要发布的内容 |
| --- | --- |
| 当前有规则 | 一条完整当前规则，说明替代此前自动项目上下文 |
| 当前为空，历史上曾发布过规则 | 一条清除说明，明确先前自动项目规则不再适用 |
| 一直没有自动规则且当前为空 | 不制造空指令，保存本次状态已确认的事实 |
| 采集失败 | 停止新请求，保持等待明确发布的状态 |

清除说明仍有必要，因为旧规则可能存在于压缩后的语义上下文里。它只撤销自动项目来源，不删除用户指令或工具读到的资料。

文件变化与窗口恢复发生在同一请求边界时，只发布最新快照一次，不先恢复旧 P1 再立即替换为 P2。该发布确认后，同一窗口中后续未变化请求不再重复。以后又跨过一次成功安装的压缩窗口，再产生新窗口的一次发布。

正常 Inline 响应后的继续推理、任务结束后的下一条用户消息、重开存档后的首次发送，都使用这一判断。不能只把补发逻辑写在工具循环的一处分支里。

## 存储身份决定恢复位置

检查点仍校验 Session、Turn、请求序号、旧窗口、新窗口、模型、原历史覆盖数及 source_sequence。新增的项目窗口状态必须与这些已提交事实对应，不能通过当前 UI 选择或磁盘文件修改时间推导。

纯请求核对记录只增加日志外层序号，不改变 compaction 所覆盖的协议历史边界。项目实际发布是历史变化，才会推进对应边界。新窗口发布的确认同样沿现有单写入者进行，不增加第二份会话日志。

恢复到“检查点已保存，下一请求还没有开始”的会话，继续时应恰好补一次。恢复到“补发已经确认，但网络尚未完成”的会话，则恢复这个项目项，不再无条件补第二份。若项目文件此后又变了，仍可根据正常变化机制发布新状态。

项目原文与历史请求引用不能因裁剪工作窗口而丢失。查看旧请求时仍用原快照；继续运行则用当前目录重新采集。源文件已不可用不妨碍打开存档，但会阻止未经成功采集的新请求。

## 新窗口计量跟随真正的发送序列

项目文件的 **32 KiB** 限制控制一次规则链的原始材料，不是整个聊天窗口或整个会话存档的限制。模型请求仍受完整序列化的 **32 MiB** 限制，两者分别判断。

项目正文、路径标题、角色包装、替换与移除说明都作为协议项进入 token 估算。一个快照另行持久化，不因此重复计量；旧窗口里尚未压缩的 P1、P2 等版本都是实际输入，不能只算最新版本，也不能先删除旧项来降低估算。

未压缩时，已有服务端用量锚点覆盖稳定的历史前缀，新发布项目项作为新增尾部估算，无需因文件改变清空锚点。成功安装压缩窗口后沿用已有清除旧锚点的行为，按新的实际历史、固定基础与工具定义重新计算，包含即将重新发布的完整项目正文。

发生压缩的响应用量仍是那次请求的事实，不直接冒充新窗口当前占用。缓存输入不从上下文占用中扣除；compaction 密文的长度估算也不被表述成解密后精确 token 数。请求超限明确失败，不裁剪已发送消息或工具结果。

## 用真实压缩验证窗口转换

通过真实应用与现有模型请求取得 Inline compaction 事件，核对完整响应保存、结果封闭、检查点确认和安装的先后关系。不能伪造 compaction 或 encrypted reasoning 来宣称服务行为通过，也不新建测试／Benchmark／Example 程序。真实运行未触发的服务端路径如实记录，不用普通聊天成功替代压缩验证。

本增量需要核对以下相互独立的结果：

- 文件未变，成功安装新窗口后的第一请求带一次完整规则，之后相同窗口不再追加。原 compaction 项及其他原始项顺序保持不变。
- 压缩边界附近文件变为 P2，只追加当前 P2 一次。文件全部删除时追加清除；一直为空时不制造空消息。
- 多工具调用的响应发生压缩时，所有调用都有匹配结果，新项目项不插入配对中间。Steer 和后续用户输入仍保留原身份与顺序。
- 保存并重开已压缩会话，分别核对尚未补发和已经确认补发的恢复位置，前者补一次、后者不重复。恢复不重跑旧工具。
- 检查点确认失败不安装新窗口，项目发布状态不先行推进。只能通过不破坏现有数据的实际可观察路径及静态状态检查获得证据，不为制造错误清空存档或凭据。
- 用量投影包含完整项目项和包装，旧版本未压缩时都计量，压缩后旧锚点失效，新窗口按实际内容估算；32 MiB 超限没有网络发送和静默裁剪。

当前状态展示改变时，BRP 使用真实输入、截图和 ECS 只读查询核对；结束后释放 Pointer 并确认 inactive。验证保持 Windows x64／DX12／PowerShell 7 以及现有账号和数据目录，不能通过重登或切账号强制触发恢复。

## 工程范围

本步只扩展项目状态与现有压缩、归档、计量的衔接，不替换原协议历史管理，也不改变固定基础快照和工具定义。Conversation 管候选与安装，Runner 等待提交，Store 保持单写入者，LLM Model 保留原始协议表示；Agent 和 Bridge 不引入 Bevy。

任务进度记录保留真实证据、失败及未覆盖行为。按影响执行格式、编译和 Clippy 检查，并同步会话、请求、存储和上下文压缩设计。代码注释与提交信息使用英文。日志只记录窗口、请求身份、摘要、大小和结果类别，不记录规则全文、聊天、凭据、reasoning 或 compaction 密文、图片 Base64。
