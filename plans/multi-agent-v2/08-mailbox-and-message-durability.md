# 建立持久 Mailbox 与消息接纳

## 目标与交付边界

建立可靠消息队列，区分消息投递、接收、消费，并支持 Agent Runtime 卸载期间留存消息。

本增量的交付是一个可以单独运行和观察的功能边界，包含实现、必要的状态/协议衔接、相关文档同步和下列验收。不实现对外 send_message/followup_task 工具。

## 设计与行为

消息身份、顺序、发送者/接收者、QueueOnly/TriggerTurn 模式、Mailbox 持久事件、watch 通知、去重与消费提交。

### 与现有架构的关系

该能力归入 Agentelier 已有的 `agent/runtime`、`agent/conversation`、`agent/turn_runner`、`agent/session_store`、`agent/tools`、`agent/llm_model`、`agent/prompts` 和 Bridge 边界中实际承担该职责的模块。不得为了照搬 Codex 目录而建立平行 Runtime、平行 Conversation 或第二套会话存储。跨领域依赖遵守 `rules/architecture.md`：允许 `ui → agent`、`ui → bridge`、`bridge → agent`，禁止反向依赖。

### 必须保持的不变量

消息接纳确认先于发送方成功回执；同 ID 同内容去重；同 ID 不同内容冲突；卸载时不丢消息；消费事实提交后才移除。

## 验收场景与通过标准

向运行中 Agent 和空闲 Agent 分别投递 QueueOnly 消息，确认两者都持久接纳但不唤醒空闲目标；重启/卸载接收方 Runtime 后投递消息，确认 Mailbox 保留；恢复后按原顺序只消费一次；重复相同消息 ID 不重复执行，不同载荷复用 ID 返回冲突；在投递和消费提交边界中断进程，重开后状态应分别为未接纳或待消费，不得静默丢失；多个消息到达时 Wait 通知不能漏唤醒。

## 验证方式

检查 Session Store 序号、Mailbox 状态、消息消费记录与真实 Runner 输入；使用日志/调试观察，不添加测试程序。

项目禁止新增或维护自动化测试代码、Benchmark 和 Example。验收应使用真实应用、模型交互、日志、运行状态、存档核对和必要的 BRP，不把这些场景写成测试程序。Root 模型固定为 `gpt-6.2-sol`；需要子 Agent 时，只选择当前目录中已确认属于 GPT-6 及以上且非 Astra 级别的模型。实际 slug 和推理等级必须记录。

## 失败处理

所有失败都应保留 Agent ID、Session ID、Agent Path、原始 Turn/call ID、操作阶段和实际错误类别。若结果未知或持久化回执不确定，应阻断可能重复的副作用，先读取权威状态；不得通过重新 Spawn、重复消息或重放工具调用来掩盖不确定性。

## 消息生命周期

消息从发送方构造开始，经过目标解析、Mailbox 接纳、接收方可见、消费开始和消费确认。消息接纳是发送成功的最小提交点；消费确认是允许从待处理队列移除的提交点。若目标 Runtime 不驻留，Mailbox 仍由 Session 级持久状态保管。

## 额外验收边界

- 在接纳提交前崩溃，发送方不得得到成功回执；恢复后不应出现该消息。
- 接纳提交后、通知接收方前崩溃，恢复后消息仍待消费并能唤醒目标。
- 消费开始后、消费确认前崩溃，恢复状态必须明确为处理中断/结果未知，不得简单当成未消费并无条件重放副作用。
- 两条消息严格按持久序号处理；同一时刻到达的消息有稳定顺序。
- Mailbox 关闭后拒绝新消息并返回 Session 正在关闭的错误；关闭前已接纳消息排空或保留为待处理。
- 队列容量达到上限时返回资源忙，不丢弃最早消息或覆盖未消费内容。
