# 为每个逻辑 Turn 冻结一致的记忆材料

本增量改变普通 Root 请求使用记忆的时机，并处理用户纠正后旧材料的失效。它依赖分类发布已存在，但不改变人格在 Session 内的固定快照。

## 每个逻辑 Turn 选择一次发布

新普通 Turn、实际启动的 Queue、主动 Retry 和新 Session 首轮，在合法接纳边界取得当时最新已发布且符合工作目录范围的记忆。未发布候选不能进入请求。

快照记录发布身份、记忆纪元、全局与项目范围、实际注入正文/索引、来源和内容摘要。该 Turn 后续的模型—工具往返继续使用同一份材料。Steer 沿用原任务边界；认证重发复用冻结字节。服务端 compaction 后重新提供当前任务固定材料，不重复追加到协议历史。

`search_memory/read_memory` 在普通任务中绑定同一发布和范围。后台新发布不修改正在执行的读视图。任务完成、取消和回收后释放引用；冷恢复依赖实际保存的请求材料与结果事实，无法还原时明确阻止续接，不猜测历史内容。

## 修订使旧快照失效

明确记住/纠正/忘记、来源删除和重置可能使旧快照不再允许使用。受影响的旧读视图必须失效，不等待后台整合完成才停止召回。下一请求准备时移除失效材料并记录原因；正在发送的请求无法撤回，已发送字节和历史事实保持原样。

如果无法准确判断旧快照是否含有被修订内容，应保守停用相关派生记忆。记忆管理 Session 可以在移除失效材料后，根据真实修订回执报告已保存或等待整合；只有发布成功才表示新摘要生效。

## 缓存与预算

稳定 Origin 身份保持在稳定 Developer 前缀。记忆和当前任务状态作为动态材料，不在固定人格中加入实时心情或不断变化的时钟。只在逻辑任务边界刷新，不在每个工具回执后重新拼接全部材料。新记忆不能挤掉用户输入、工具配对、项目约束和任务状态。

## 完成条件

- 同一 Session 连续多个逻辑 Turn 中，第一轮使用 P1，后台发布 P2 后下一轮使用 P2；当前 Turn 的所有工具往返仍使用 P1。
- `search_memory/read_memory` 与当前 Turn 绑定相同发布身份和范围。
- 用户纠正或忘记后，旧派生材料在下一请求准备时失效；历史请求字节不被修改。
- Queue、Retry、Steer、认证重发、compaction 和恢复遵循现有请求快照语义。
- 后台发布失败时仍可使用未失效的上次有效发布；首次无记忆时普通聊天仍可进行，并区分空记忆与存储不可用。
- 实际请求检查能核对记忆发布身份、范围、内容摘要和 Developer 注入位置。

## 工程边界

- 目标环境为 Windows x64、`x86_64-pc-windows-msvc`、DX12 与 PowerShell 7；不为未要求的平台增加兼容层。
- 遵守现有 Workspace / Crate 职责和依赖方向。业务实现放在 `crates/`，不在 `app/` 增加业务逻辑；不修改 Bevy、Widgetry、BRP 或 Codex 上游源码。
- 复用 Account、LLM Model、Runtime、Conversation、Session Store、Memory、Project Context、Skills、ToolCatalog 和现有异步任务机制；不建立平行 Agent Registry、任务数据库、记忆数据库或 Skill 管理器。
- 不恢复用户可见的提示词管理页面、Project Skill 或人格工作台。不得通过人格、记忆或 Skill 扩大工具权限。
- 不接入 B 站账号，不执行浏览、评论、私信、上传、直播、定时发布或其他平台运营。
- 未经用户明确授权，不退出登录、不重新登录、不切换账号、不重置凭据，也不通过更换数据目录破坏登录状态。
- 项目禁止新增或修改测试代码、Benchmark 和 Example。按变更范围使用 Cargo 编译、格式、Clippy、真实应用运行、日志/请求/存储状态核对；涉及 GUI 可观察行为时必须使用实际应用和 `bevy_brp_mcp` 验证。
- 不声称未执行的验证已经通过。发现问题在对应功能增量内修复并复验受影响范围，不另设纯验收阶段。
