# 为未完成调用保留结果空间并安全压缩

本增量让开放调用在上下文增长和 Inline 压缩时仍能得到唯一的原调用结果。交付物是统一的结果/图片预留、发送与响应接纳两侧容量检查、安全压缩检查点，以及与非法压缩失败绑定的一次性继续动作。

顺序承接 [05 · 独立执行](05-isolated-execution.md)，随后进入 [07 · 同 Turn 非阻塞](07-nonblocking-tools.md)。前一增量提供有界执行契约，本增量把“将来结果必须放得下”纳入准入；下一增量才让模型真实在 pending 期间继续请求。本阶段先建立容量与压缩规则，不能为验证这些规则提前解除仍在使用的整批采样屏障。

## 结果必须先有可靠的历史入口

工具只回报结果事实。Conversation 校验来源与当前任务状态；图片先由 Store 提交为本会话附件，再确认工具结果；边界追加 `function_call_output` 时核对原始调用仍存在、结果尚未追加、任务与载荷一致。完成这个步骤后才允许构造使用它的请求。

一次追加失败不能让 UI 或 Runner自行补一份结果。重复通知由账本当前状态去重；相同身份但不同结果必须阻断该会话后续执行并显示冲突。完成通知只是唤醒信号，每次进入请求、等待和收尾边界都重新检查账本，避免一次通知丢失导致永久悬挂。

若结果已在历史中，而承载它的请求断流或超时，保留该结果及请求未知事实。后续请求重放相同历史，不重新调用工具。原用户任务已产生副作用或已保留步骤时，原有整 Turn Retry 限制继续生效；界面的“处理已完成结果”也不等于重跑原任务。

## 预留覆盖整个结果，不按到达顺序抢空间

多个任务可以同时完成，结果预算因此需要在同一会话所有者处结算。每个执行器必须有可依赖的输出上限；当前 64 KiB 文本、单图 4 MiB、工作上下文图片累计 16 MiB、完整请求 32 MiB 等限制继续有效。图片按不可变附件身份去重，不能通过同时返回而各自看到“还有空间”。

接纳异步调用时预留它可能产生的有界结果，包括协议封装和必要终止说明。图片可能出现的调用按其声明上限参与预留，直到得到结果后结算；无可靠上限的执行器保持同步或先建立结果限制。实际超出声明的载荷产生明确错误结果，不能默默截断成成功输出。

预留不是第二份载荷。待保存、已保存未追加、已在工作窗口的同一结果不能被重复计量；历史附件存档也不等于活跃上下文占用。多个大结果同时完成时，原调用仍必须有一个可解释的结果或错误，不因内存/发送预算被悄悄删除。

文本、图片、协议封装和必要终止说明都来自执行器的有界契约。执行状态变化只改变预留与实际占用的归属，不把同一载荷复制成新的预算项目。这样多个任务同时完成时，后到结果不会因为先到结果占满窗口而被删掉。

## pending 决定本次请求能否压缩

这里的 pending 是协议概念：原始调用已经在历史中，但唯一对应 output 还没有追加。执行已结束、结果还在保存，也仍是 pending；相反，`exec_command` 已返回 `session_id` 后，进程继续运行不属于原函数的 pending。

本次采用保守边界：

1. 冻结请求快照时，只要还存在未配对调用，就不发送 Inline `context_management` 配置；不在请求发出后因任务刚完成而改判断。
2. 调用全部闭合后，恢复现有 Inline 压缩。压缩仍由普通 Responses 请求承载，计入原模型请求预算，不新增独立轮询或自动重试循环。
3. 返回的 compaction item 必须位于没有未闭合调用的合法历史位置，才允许作为替换边界。安全 compaction 在新 async call 之前时，可以保留该调用和后续结果关联。
4. 如果服务返回了越过未闭合调用的 compaction，整份响应在正常历史接纳、任务登记和副作用派发之前失败；保留请求错误与安全诊断，不安装这份响应或压缩窗口。

上述先后关系是协议检查条件，不是后台任务运行状态的简写。`exec_command` 的函数结果已经闭合时，仍存活的进程由自己的资源登记管理；不能为它无限关闭压缩，也不能因普通执行器结束就绕过尚未提交的 output。

## 非法压缩失败后，继续动作只作用于一次请求

第 4 种情况不自动重发一套不同请求。错误状态提供一次性的“本次不压缩并继续”动作：绑定这次失败请求及原输入引用，确认没有新的用户 Turn 取代它后，从当前合法历史继续，只对这一次新请求省略压缩。已经追加的用户输入与工具结果不再追加，未提交的原输入按原身份接入；先前副作用不重跑。动作产生新的请求身份并计入预算，容量不足时保留输入并拒绝发送，再失败时停止，不循环重试。应用不能把非法响应当成已经成功接纳的工具批次。先前任务的结果仍按合法历史边界保存与追加，不被失败的压缩响应拖住。

官方文档说明了[有序保留不透明压缩项](https://developers.openai.com/api/docs/guides/compaction)的方式。此处的 pending 约束是本方案根据原始调用关联设定的应用规则，验收需要检查真实请求和结果续接，而不只检查本地列表还留着一个 ID。

本增量交付该动作的业务身份、条件检查和回执，界面的具体按钮随 12 接入。它与整 Turn Retry、普通发言、重新执行工具都不同：只有当前失败请求仍可续接且容量允许，才从合法历史产生一次新的请求。按钮尚未落地时不能用本地业务分支验证冒称点击验收已完成。

## 在输入与候选响应两侧守住余量

若 pending 期间把窗口填满，即使任务最终完成，也可能没有空间容纳结果和下一次安全压缩请求。因此在接纳新异步调用、应用用户输入、继续模型请求时，都要核对以下总量：现有工作上下文、新材料、全部未配对调用的最大已预留结果、终止/控制输出和下一次合法请求需要的余量。

有余量才允许新增；逼近边界时停止新增异步工作和会扩窗的模型请求。输入保留为草稿或明确排队项，界面显示“等待后台结果以释放上下文”。这时的等待和取消由本地任务控制完成，不能要求模型再发一个 `wait_for_tasks` 才能解锁。

预留也在候选响应接纳时重新核对。新正文、reasoning、调用参数及新任务结果预算不能吃掉旧 pending 已有的预留；越界响应在正常历史接纳和新任务派发前失败，保留已确认历史与旧任务的结果空间。否则仅限制发送前输入，仍会被一个较大的响应绕过。

结果追加使调用闭合之后，再在下一次允许的请求中恢复压缩。若服务输出、能力元数据变化或异常大材料仍使预算无法满足，则保持历史和结果、明确停止续接；不裁掉未配对调用，不伪造摘要，也不为了发送成功丢用户输入。容量是有限功能边界，不承诺后台任务无限存在时还能无限聊天。

使用实际模型目录能力和现有估算器计算余量；未知能力保留未知，不制造虚假的精确 token 数。请求实际序列化大小仍是发送前的硬检查。工具结果到达、用户 Queue、目录设置和状态展示更新不得共同重复抬高已覆盖的 usage 锚点。

## 检查点只覆盖冻结的历史前缀

checkpoint 绑定协议历史位置与被覆盖前缀，不绑定包含所有 UI 变化的全局版本。任务从 Running 变成完成、名称修改或 Queue 入队，不应让本来合法的压缩不断失效。

准备 replacement 时保留 compaction 之后的调用与未配对集合；持久化 checkpoint，确认后核对原历史前缀并安装新窗口。冻结之后确认的尾部结果或输入必须在新窗口尾部保留，不能由旧快照覆盖。若前缀不一致或回执不确定，阻断继续发送并重新加载权威存档。

原始公开时间线、任务身份和附件不因工作窗口裁剪而删除。调用尚未闭合时不跨过它的原始位置，也不从任务列表重新拼一份“补发调用”来修补被裁掉的历史。项目规则与 Skills/记忆材料仍按原有窗口与来源规则补发，调用模式和管理工具 schema 也进入请求计量。

## 本增量如何取得证据

运行验收使用 Windows x64、DX12、PowerShell 7、当前锁定依赖和真实应用。涉及服务时使用现有 Sign in with ChatGPT 与 `gpt-6.2-sol`，不自动换模型或登录路径，不为凑边界次数重复调用服务。编译、格式和静态检查只覆盖本增量实际改动及直接影响；构建成功不能代替运行证据。

在现有数据环境中正常创建专用验收会话，可写命令限定于明确的验收工作目录，保留原有会话、文件和登录。恢复或损坏记录场景先备份该验收会话及附件，只处理已备份副本并记录实际读取位置。退出、切号、重新授权、凭据重置或以切换数据目录间接使登录失效，仍须已有明确授权；清单不提供这项授权。正常关闭后在同一环境重开与退出账号不同。

不编写或引入测试、Benchmark、Example、mock 服务、专用 harness 或仅为验收服务的依赖。可以直接运行应用、检查正常诊断状态，或在调试器中控制真实应用的完成、回执和事件处理边界。难以触发且没有观察入口的条件标为未覆盖。

| 标记 | 证据及其边界 |
| --- | --- |
| 静 | 实际源码、依赖方向、序列化与错误路径审阅，只证明规则被表达，不能替代交错运行或 GUI/服务结果。 |
| 调 | 调试器控制真实应用边界或查看正常诊断状态。人工响应、事件必须标明注入位置，不称为服务实际返回。 |
| 运 | 真实应用与正常工具、存储记录、进程事实、关联日志；GUI 行为还需要 BRP 的真实输入、截图或安全 ECS 查询。 |
| 服 | 真实 Responses 请求/响应的安全记录及原调用关联；需要验证结果使用时，由模型准确复述工具独有随机标记。HTTP 200 本身不足以证明非阻塞或生命周期正确。 |

每条记录场景 ID、实际前提、操作、预期事件顺序、观察结果、证据位置、通过状态及清理结果，以会话、来源 Turn、请求、任务、原 `call_id` 和提交序号关联。日志只留必要安全字段，不导出凭据、隐藏 reasoning/compaction 或敏感完整正文。未执行、故障前提未达到、证据不足均不标通过；后续修改只复核直接受影响的证据。

涉及新增按钮或可观察 GUI 行为的完整验收，使用实际安装的 `bevy_brp_mcp` 发现应用与方法，优先按稳定 `Name` 找控件。Pointer、Keyboard、Focus、Scroll 走真实输入，不直接改 ECS 后声称交互通过；分别核对工具接纳、输入执行完成和目标行为。检查有意义的中间帧及最终收敛。结束后通过已发现的 `brp_extras/pointer_control` 执行 `release`，查询 `status` 至 `phase=inactive` 并检查 `last_error`；`busy=false` 不能单独证明成功。BRP 无等价能力的 OS 行为另以真实环境证据说明。

### 发送行为与局部分支分别记录

C-02、C-05、C-07、C-08、C-10 可在现有应用的提交、序列化和候选响应边界验证；人工 compaction 或超限材料要明确标注注入位置。C-01 当前核对冻结配置及三种 pending 判定，C-04、C-06 当前核对闭合/窗口关联；07 开放非阻塞后补真实 pending 请求与结果续接的服务证据，13 再复核跨 Turn 容量场景。服务没有产生安全 compaction 位于新调用之前的形态时，C-06 的局部调试不能替代真实服务覆盖。

C-03 当前验证业务容量拒绝、原输入身份和本地控制仍可推进；任务界面的说明、草稿与 Queue 可观察行为在 12 以 BRP 复核。C-09 当前实现并检查一次性动作的业务范围、重复/取代/容量/再次失败分支；按钮操作在 12 补 BRP，正常服务继续则保留独立服证据。清单中的待补条件不因本阶段代码编译或调试分支通过而自动完成。
