# 从已确认事实恢复任务和结果

本增量让独立保存的调用、结果与交付状态能够在重开会话时还原。恢复依照最后一份已经确认的事实区分未执行、结果未确认和已保存结果，并且每次恢复得到同一份身份与唯一输出。

上一份：[让调用与结果在历史中分别提交](03-open-history.md)。下一份：[让每次执行带着固定来源](05-isolated-execution.md)。本增量消费上一份定义的开放历史和持久事实；下一份调整独立执行材料与资源准入，它与恢复的技术职责不同，执行顺序相邻不意味着恢复器负责启动执行器。

恢复只还原数据，不重跑历史工具，不重新连接 OS 进程，不自行发模型请求。当前运行仍按批次等待；真实多任务并发和跨 Turn 产生的恢复材料，在方案 07 与 13 开放后补运行证据。

## 恢复沿用原调用身份

每个工具调用都保留以下关联，原生异步调用另有应用分配的稳定任务 ID。

| 身份 | 用途 |
| --- | --- |
| 会话 UUID | 隔离历史、任务、进程与附件 |
| 原始 Turn ID、请求序号 | 说明工作由哪次用户任务和响应产生 |
| 原始 `call_id`、输出项 `id` | 分别关联协议结果及校验响应项 |
| 应用任务 ID | 供查询、等待、取消和 UI 稳定定位；会话内永不复用 |
| 本次执行实例身份 | 识别当前进程中的真实执行，拒绝旧句柄或旧通道的迟到回报 |
| 来源契约与调用上下文引用 | 固定工具来源、参数、目录、原始用户陈述、记忆纪元及能力 |

UI 物理行号、当前 operation 和当前 request_index 都不是任务身份。原任务完成于 Turn 3，也不会把来源改成 Turn 3。恢复后沿用保存的任务身份，运行句柄重新从“无”开始；它们不可从存档复活。

同一会话里，已经成功、取消、未执行或结果未知的历史任务都继续占据其身份，不能因为 UI 收起或已交付就复用。协议历史中的调用、任务记录与附件互相核对；无法找到原调用时，不创建孤立 output 来让列表看似完成。

## 结果恢复仍通过唯一交付出口

工具只回报结果事实。Conversation 校验来源与当前任务状态；图片先由 Store 提交为本会话附件，再确认工具结果；边界追加 `function_call_output` 时核对原始调用仍存在、结果尚未追加、任务与载荷一致。完成这个步骤后才允许构造使用它的请求。

一次追加失败不能让 UI 或 Runner自行补一份结果。重复通知由账本当前状态去重；相同身份但不同结果必须阻断该会话后续执行并显示冲突。完成通知只是唤醒信号，每次进入请求、等待和收尾边界都重新检查账本，避免一次通知丢失导致永久悬挂。

若结果已在历史中，而承载它的请求断流或超时，保留该结果及请求未知事实。后续请求重放相同历史，不重新调用工具。原用户任务已产生副作用或已保留步骤时，原有整 Turn Retry 限制继续生效；界面的“处理已完成结果”也不等于重跑原任务。

这一规则也作用于恢复补回的结果：实际载荷已经保存时从原存档使用它，尚无可信载荷时只能形成明确的恢复终止说明。不可让“再加载一次”变成再次执行工具、再次写入 stdin 或重复追加结果的隐式重试。

## 确认事实决定恢复可以知道什么

跨 Turn 之后，日志不能再只保存“一批已经封闭的调用”。它需要独立表达合法响应、调用登记、执行开始、结果形成、历史追加和前台结束。仍使用现有 Session Store 单写入者、连续序号、Flush/sync 回执与本会话附件存储，不引入另一套任务数据库。

下面列的是必须表达的业务事实，事件名称在实现时可沿用或调整现有类型。

| 事实 | 持久确认与后续动作的关系 |
| --- | --- |
| 输入与请求准备 | 保存原输入身份、冻结历史前缀、来源材料、包含的结果集合及实际发送阶段 |
| 响应接纳与任务登记 | 完整响应和全部调用到任务的映射在一个原子追加记录中确认；之后才允许派发 |
| 执行开始 | 每个副作用开始之前确认；等待资源的登记不冒充已开始 |
| 工具实际结果 | 先提交图片附件，再保存带原始身份的不可变结果；保存成功才可用于历史 |
| 历史追加 | 记录所追加的唯一 output 及前后历史位置；不能用一份较旧 Session 快照覆盖后续事实 |
| 取消与资源清理 | 保存请求范围、执行终态与实际回收事实；取消请求和资源回收分开 |
| 前台终态 | 只表示前台结束和真实回收，不把所属异步任务强制改成未执行 |
| 压缩检查点 | 保存被覆盖的历史前缀、替换窗口、未配对调用关联和来源材料边界 |

任务 ID 在准备响应接纳记录时分配，随响应和映射一起提交，提交成功后才公开。崩溃不能留下“响应已接纳，但任务 ID 映射另存失败”的空隙。所有调用先通过身份、参数上限、模式和重复性校验；无效完整响应不进入正常可重放历史，也不启动其中任何工具。

同一记录的提交结果不确定时，沿用当前游标阻断语义，不盲目重新追加。结果已经取得而保存失败时，保留内存载荷、停止新的请求与副作用派发、暂停 Queue，继续回收必要资源。保存失败不撤销已经修改的文件。已有结果不以“再执行一遍工具”补救。

## 逐个崩溃窗口还原数据

恢复只还原数据。加载日志后，先重建唯一历史、任务映射、结果事实与来源，再决定哪些任务需要中断占位。占位也必须持久确认，并标记为恢复产生的终止说明，不能伪造成工具的实际成功输出。

| 最后确认的位置 | 恢复行为 |
| --- | --- |
| 仅有请求准备或部分 SSE | 保留发送/部分展示事实；没有合法完整响应就没有可执行新调用 |
| 响应与登记已保存，开始记录尚无 | 记为 `NotExecuted`，为原调用补唯一的未执行结果 |
| 开始已保存，结果未保存 | 记为 `Unconfirmed`；副作用可能发生，补明确的未知结果说明，不重跑 |
| 附件已提交，结果记录未提交 | 附件不是调用成功证据；任务按结果未确认处理，不从文件存在猜测输出 |
| 结果已保存，尚未追加历史 | 使用已存载荷补唯一 output，不再次执行 |
| output 已追加，尚未准备后续请求 | 保留“已保存，待处理”，等待用户明确继续 |
| 请求已经发送，但完整响应缺失 | 保留请求结果未知；下次重放同一历史与同一结果，不重执行工具 |
| 前台 Finished 已保存，原工具后来完成 | 继续从任务事实重建旧来源工具，不能用 Finished 的旧快照覆盖结果 |
| 已发起取消，回收尚未确认 | 显示上次结束未确认；不从取消请求推断远端或本地副作用已经撤销 |

进程登记恢复为历史资源记录，不连接旧 PID、不猜测恢复 stdin/stdout。Windows 进程的实际关闭保障继续由现有 Job/句柄机制承担；下次打开时只陈述已保存的清理证据。旧 `session_id` 不得复用。恢复产生的“历史清理未确认”与本次进程中仍持有的待回收句柄分开：前者可作为持久终止证据，允许只读查看和会话替换，不等待重启后永远不会到来的 OS 回执；若涉及未知外部副作用，按明确的继续执行确认控制新派发。

重复加载应得到相同结果，不重复追加恢复占位。仍按现有规则处理残缺末行：先备份、校验前缀再规范化；中间损坏、重复序号、身份冲突和损坏附件明确拒绝，不以“恢复异步任务”为由覆盖原件。

已有同步历史继续可读；缺少异步字段对应同步模式。新增状态按本次真实需求表达，不建设多版本迁移框架，也不要求把旧历史重写成异步历史。恢复后的任务唯一性包含已经完成、取消和未知的历史任务，不能因列表收起而忘记这些身份。

这张表区分“开始记录已保存”和“实际副作用已经发生”。开始记录之后立即崩溃，即使观察不到文件产物，也只能说结果未确认，不能反推未执行。相反，仅有完整响应和登记而没有开始确认时，恢复补 NotExecuted；应用不能为了得到好看的确定状态而试着重新执行。

未知外部效果的继续门槛保留原始任务与来源：它暂停相关新副作用派发和自动 Queue，只有用户明确核查并确认指定任务/范围、且该确认持久保存后才能解除；普通聊天或 Queue 恢复不能替代。当前仍存在的活句柄、身份冲突与存储未确认不能由这种确认绕过。完整控制动作在方案 09 与界面增量提供，本阶段恢复数据不得把该门槛静默清除。

## 文件原件、当前句柄与读取来源分别保护

恢复读取使用现有 Session Store 连续序号、前缀校验和附件身份。残缺末行仅在原件备份与前缀验证成立后规范化；中间损坏、重复序号、调用/任务来源冲突或损坏附件都明确拒绝，保留材料供核查，不从错误之后继续猜测正常历史。

响应与任务映射必须是同一已确认追加事实，不允许读取出响应已接纳而任务映射缺半份的状态。结果存在但 output 尚无时，可以在确认边界补一次；output 已有时不再追加。恢复占位自身也须持久确认，重复打开只读到同一个恢复结果，不再次生成新的占位或新任务 ID。

历史记录中的进程 ID 和资源清理未确认，只陈述上次已知情况；当前进程中的句柄集合从空开始。已保存的退出摘要可以供查看，不能拿旧 PID 或 session_id 恢复控制能力。Windows 的 Job 与句柄关闭机制仍负责实际进程保护，数据恢复不制造一套进程重附着方案。

前台 Finished 只表示前台事实。后续出现相同来源任务的真实 ToolReturned 或资源终态时，读取必须继续保留，不能退回第一份 Finished 的整会话快照。长期记忆最终怎样按来源闭合、连续前缀和纪元读取，由方案 11 完成；此处保留完整来源事实，避免恢复提前丢掉它需要的证据。

## 验收必须知道应用究竟读了哪份记录

运行验收使用 Windows x64、DX12、PowerShell 7、当前锁定依赖和真实应用。涉及模型服务时使用现有 Sign in with ChatGPT 与 `gpt-6.2-sol`，不自动替换模型、登录路径或工具契约；本方案形成的文档本身不代表已经通过构建或运行验收。编译和静态检查只覆盖此增量实际影响的范围，遵守 [项目约束](../../rules/project-context.md) 与 [常用命令](../../rules/common-commands.md)。

在现有数据环境中正常创建专用验收会话，保留其他会话、登录和文件；可写工具仅操作明确的验收工作目录。不得为验收重置数据目录、删除原会话或复制认证材料。登出、切号、重新授权、凭据重置以及会导致登录失效的数据目录变更，仍须已有明确授权；清单不是这类授权。未授权的分支保留静态证据并标为未执行。

不编写或引入测试、Benchmark、Example、mock 服务、专用 harness 或测试专用依赖。使用真实应用、正常工具、既有诊断和调试器边界观察；无法实际到达的条件记录为未覆盖。四类证据分别记录：

| 标记 | 证据与边界 |
| --- | --- |
| 静 | 源码、依赖方向、序列化、状态转换和错误路径审阅；不能证明真实交错、服务或界面已工作 |
| 调 | 调试器控制真实应用边界或检查正常诊断；人工替换响应/事件注明注入位置，不能称为服务实际返回 |
| 运 | 真实应用、正常工具、存储记录、进程事实和关联日志；涉及 GUI 时使用 BRP 真实输入与状态/截图，不能仅靠本地状态推断服务已使用结果 |
| 服 | 真实 Responses 请求/响应的安全记录及关联结果，必要时准确复述工具独有随机标记；HTTP 200 本身不足以证明完整行为 |

每项记录场景 ID、实际前提、操作、预期顺序、实际结果、证据位置、是否通过和清理结果；关联会话、来源 Turn、请求、任务、原 `call_id` 与提交序号。只记录必要的安全字段，不导出凭据、隐藏 reasoning/compaction 或完整敏感正文。实际日志沿用 [日志规则](../../rules/logging.md)。

未执行、故障条件未达到、只取得部分种类证据，均不把整项标为通过。后续增量改变这里的边界时，复核直接受影响的项目，保留未受影响证据，不机械重跑全仓检查。

每次故障场景先备份专用验收会话的记录和必要附件。需要构造残缺尾部、损坏、重复序号或附件错误时，只处理已备份的验收材料副本，记录副本路径、原件备份及真实应用实际读取的材料。不得为方便建立另一个空数据目录而使现有登录失效，也不得处理其他会话。普通关闭后在同一数据环境重新打开，与账号退出分开。

可用调试器停在指定的已确认位置，再受控结束并重开真实应用；无法到达该位置时保留未覆盖，不编写故障注入 harness。实际写盘、Store 回执到达、业务确认三个时间点要分别观察，不能把“调试器暂停了回执”误写成“磁盘没有写”。

R-01–R-07、R-10、R-11 可在当前保守工具执行和独立保存边界下取得主要证据。R-08 的真实 Finished 后晚到工具，需要方案 13 开放生命周期后补运证据，本阶段仅核查恢复状态机和在真实读取边界的明确局部材料。R-09 的新取消/进程范围、历史未知继续门槛、记忆前缀效果分别随方案 09、10、11、13 联动；这里先验证不恢复旧句柄、不复用身份和历史未知/本次资源的区别，不能把尚无前提的完整条目算通过。

R-06、R-07 正常明确续接若在当前保守路径即可发生，仍需对应真实服务或标注清楚的传输调试；仅检查恢复列表不能证明服务使用了结果。统计恢复后是否自动发请求时只计算聊天/工具结果续接，既有记忆后台请求按来源另记，显式 Queue 的用户意图也单独记录。
