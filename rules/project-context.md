# 项目背景与目标环境

## 目标平台

- 操作系统：Windows 64 位。
- Rust Target：`x86_64-pc-windows-msvc`。
- 图形后端：DX12（wgpu backend）。
- 命令执行环境：Windows 下统一使用 PowerShell 7（`pwsh`），不使用 Windows PowerShell 5（`powershell.exe`）。

工程设计、实现和验证均以此环境为前提。

项目不以跨平台兼容为当前目标。除非任务明确要求改变平台支持范围，否则：

- 不为 Linux、macOS、Web 或 32 位系统增加兼容实现、fallback、stub 或条件分支。
- 不为假设中的其他平台、Target 或图形后端增加抽象层、依赖、Cargo Feature 或额外配置。
- 不为了保持非 Windows 平台可编译而增加当前需求不需要的代码。
- 可以直接使用 Windows 平台能力，不必为唯一支持的平台额外包裹 `#[cfg(windows)]`。

这些限制不意味着禁止通用代码或条件编译。没有额外维护成本的跨平台实现可以保留；当前需求确实需要的条件编译也可以使用。

**不为假设中的未来需求增加复杂度。** 如果以后需要支持其他平台、Target 或图形后端，应根据届时的实际需求重新设计，而不是提前预留兼容结构。

## 编译期平台检查

每个 Workspace crate 的入口必须包含编译期 Windows x64 检查：

```rust
#[cfg(not(all(target_os = "windows", target_pointer_width = "64")))]
compile_error!("This application supports Windows x64 only");
```

Library 在 `lib.rs` 中检查，Application 在 `main.rs` 中检查，不在内部 Module 重复添加。

此检查用于明确拒绝不支持的 Target，不要求提供替代实现。

## 项目定位与兼容性原则

Agentelier 是供作者个人学习、实验和使用的 AI Agent 项目，不以商业发布或提供稳定公共 API 为目标。

- 各 crate 不需要发布到 crates.io。
- 不要求保持 API 向后兼容，也不为历史版本建立兼容层、弃用期或迁移方案。
- 允许为合理设计直接进行破坏性重构，以设计合理性、简洁和可维护性为优先。
- 只需保证在当前明确支持的 Bevy 版本下正常工作，不承担旧版 Bevy 兼容义务。

## 开发与验证原则

### 测试、Benchmark 与 Example 禁令

本项目不编写或维护测试代码、性能 Benchmark 和 Example 程序。

- 禁止编写、生成或修改任何测试代码，包括 Unit Test、Integration Test、Regression Test 和 Property-based Test。
- 禁止编写、生成或修改任何 Benchmark 代码或专门的性能基准测试程序。
- 禁止编写、生成或修改任何 Example 程序。
- 上述限制适用于方案探索与正式开发，不设置临时例外。
- 不采用 Test-Driven Development，不要求为功能开发、Bug 修复或重构补充自动化测试。
- 不引入仅服务于上述测试、Benchmark 或 Example 的依赖、辅助模块或基础设施。

上述限制不禁止文档中的代码片段、正常应用运行时的诊断逻辑，也不限制直接修改和运行应用本身进行技术实验。

### 允许的验证方式

禁止测试代码不等于免除功能验证。

根据任务实际影响，使用必要的验证手段确认实现是否正确，包括：

- Cargo 编译检查、构建、格式检查与 Clippy 静态检查。
- 直接运行应用，观察实际行为与运行结果。
- 使用日志、调试工具、运行时状态检查和必要的断言定位问题。
- 根据实际需要分析运行时性能表现，但不编写或执行专门的 Benchmark。
- 使用 BRP 对真实 Bevy GUI 进行自动化操作与验证。

验证范围应与当前任务及其直接影响相匹配，不要求执行无关的检查。

### BRP 自动化 GUI 验证

**BRP 自动化 GUI 验证明确允许，不属于本项目禁止的测试代码。**

涉及可观察 GUI 行为新增或修改时，必须按照 `rules/gui-debugging.md`，通过 `bevy_brp_mcp` 对实际运行的应用进行针对性自动验证。

允许使用 BRP 工具执行自动化交互、截图、ECS 状态查询、日志检查等操作，并根据结果判断功能是否符合预期。

BRP 验证属于开发过程中的运行时验证，不要求将验证流程转化为 Unit Test、Integration Test、Regression Test 或其他持久化测试代码。

对于 BRP 无法覆盖的行为，应通过适当的实际运行和调试方式验证。无法完成的验证必须如实记录，不得将未经验证的行为标记为通过。

### 验证结果

- 仅通过编译或静态检查，不代表运行时行为已经正确。
- 仅成功启动应用或工具调用成功，不代表目标功能已经正确实现。
- 发现问题后，应通过实际运行、状态检查和诊断信息确认修复结果。
- 不得声称未实际执行的验证已经通过。
- 不为满足流程形式而编写测试、Benchmark、Example 或执行无意义的验证步骤。

## 登录状态保护

未经用户明确授权，开发 Agent 在开发、调试和 BRP 自动化验证期间不得主动：

- 退出登录、重新登录或切换账号。
- 发起新的交互式 OAuth 授权。
- 清除、覆盖或重置登录凭据。
- 为调试而破坏现有登录状态。
- 通过更换数据目录等操作间接造成登录失效。

该限制不影响应用正常的账号恢复、按需 Token 续期及用户主动执行的账号操作。
