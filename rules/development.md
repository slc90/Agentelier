# 开发流程规则

## 开发流程总览

项目根据解决方案是否明确，区分方案探索与正式开发。

**方案探索**用于解决尚未明确的设计或技术问题，按照 `AGENTS.md` 的探索原则，按需理解现有设计、自由探索候选方案，并在方案确定前评估对整体设计的影响。探索阶段在工程流程方面仅强制维护任务进度记录，不受其他正式开发流程约束。

**正式开发**采用 Type-Driven Development 与小步迭代，根据明确的目标行为进行实现、验证和调整，不强制采用固定的实现步骤。

正式开发完成后，根据实际影响范围执行必要验证，并进行适用的独立 Code Review。

探索形成可行方案后，应自主衔接正式开发，不需要等待人工确认。探索代码不能未经正式整理、验证和 Review 就直接作为最终实现交付。

**所有开发阶段均须遵守 `rules/project-context.md` 的项目级约束，包括测试、Benchmark 和 Example 禁令。** 方案探索的流程豁免不适用于这些限制。

## 任务进度记录

### 创建与维护

所有实际修改仓库的任务，包括代码、配置、文档修改和方案探索，都必须维护任务进度记录。纯咨询和只读分析不需要创建。

明确任务目标后、开始修改前，在仓库根目录创建 `<任务名称>-进度.md`。

进度记录属于临时工作文件，不放入 `plans/`，不作为正式文档或最终提交内容。同一任务中断后继续使用原有记录，不得覆盖其他任务的进度文件。

记录至少包含：

- **目标与范围**：任务需要完成什么，以及不包含什么。
- **实施进度**：已完成、正在进行和待完成的工作。
- **问题与决策**：重要发现、设计决策、阻塞问题及待解决事项。
- **验证结果**：实际执行的验证、结果、失败原因及尚未验证的范围。
- **Code Review**：适用的 Review 状态、Findings 及处理情况；不适用时说明原因。
- **下一步**：中断或续接时需要继续执行的工作。

方案探索可以采用较自由的记录形式，但必须保留足以理解实验过程、重要结果和后续决策的信息。

完成重要步骤、发现问题、调整方案或取得验证与 Review 结果后，应及时更新记录。不得将未执行的验证、未解决的问题或尚未完成的工作标记为通过。

### Code Review 状态

需要独立 Code Review 的任务，必须在同一进度 Markdown 中维护 Review 状态，不另建 Review State 文件。

记录内容包括：

- 当前 `review_phase`：`initial_full`、`repair`、`incremental_review`、`final_full` 或 `passed`。
- 当前 `review_round` 及执行状态，包括尚未完成的 `pending`。
- 上一轮已完成 Review 的轮次、阶段和完整结果。
- 每轮 Findings 原文、处理情况及仍未解决的 Findings。
- Baseline 存在时的 `baseline_ref`、完整 `baseline_tree_sha` 和精确的 `excluded_progress_path`；不存在时明确记录。
- 下一步需要执行的 `next_action`。

Reviewer 尚未确认的修复不得标记为已验证解决。Review 中断或尚未取得完整结论时，不得记录为通过。

每轮 Review 返回 Findings 后，先保存 Findings，再按照 `rules/code-review.md` 建立或条件更新 Baseline，并记录返回的完整 Tree SHA，之后才能开始下一轮修复。

Review 的阶段转换、Baseline 管理、完整性校验及清理方式均遵循 `rules/code-review.md`，不在此处重复定义。

### 中断与续接

任务中断、暂停或尚未提交时，必须保留进度记录。

续接时先读取记录，核对实际工作区状态、已有验证结果及未完成事项，再继续执行。不得仅凭记录中的完成标记判断任务已经结束。

存在 Code Review Baseline 时，还必须核对实际 Ref 与记录中的完整 Tree SHA。若发生不一致，应先根据实际 Git 状态和已有 Findings 查明原因，不得静默覆盖记录或推断 Review 已通过。无法确认 Baseline 正确时，按照 `rules/code-review.md` 重新进行 Full Review。

未完成的 Review 仍为 `pending`，不得因会话中断而跳过。

### 清理与提交

正式开发任务在完成实施、必要验证及适用的独立 Code Review 后，方可进入提交阶段。

提交前删除本任务的临时进度 Markdown，并按 `rules/git.md` 检查最终提交范围，确保进度文件没有进入提交。

同时确认最终变更符合 `rules/project-context.md` 的项目级约束，不包含禁止的测试、Benchmark 或 Example 代码。

尚未完成或尚未提交的任务继续保留进度记录；任务取消时清理该任务创建的临时记录及适用的 Review Baseline。

## 工程化开发方法

### Type-Driven Development

正式实现前，先明确当前功能涉及的数据、状态、类型及其关系，包括必要的 Component、Resource、Event、Message、枚举与接口。

优先通过类型表达明确的业务语义和状态约束，避免依赖隐含约定、特殊值或松散的数据组合。

类型设计以当前需求为限，不为了形式上的类型安全或假设中的未来扩展增加无意义的 Wrapper、Generic 和抽象层。

Type-Driven Development 不要求提前设计全部内部细节。后续实现或实际运行发现类型设计不合理时，应及时调整。

### 小步迭代

优先围绕单个明确的功能或行为完成实现与验证，再进入下一个行为。

每次迭代应根据实际情况：

1. 明确当前需要实现的行为及其预期结果。
2. 完成满足当前需求的最小必要实现。
3. 通过编译检查、静态检查、实际运行或相关调试工具验证实现。
4. 根据验证结果修复问题、调整类型设计或整理代码。

上述顺序用于说明迭代思路，不要求机械执行所有步骤。不同任务可以选择适合自身的实现与验证方式。

不为假设中的未来需求提前扩展功能，也不为了保持固定流程而制造无意义的工作。

### Bug 修复与重构

修复 Bug 时，优先通过现有功能的实际运行、日志、状态检查或其他适当的调试方式确认问题。

明确问题原因后修改实现，并重新验证原有问题是否消失，以及直接受影响的行为是否仍然正确。

纯重构不要求人为制造新的验证场景，但应根据实际影响确认原有可观察行为未发生非预期变化。

实现与重构过程中发现职责划分、类型设计或代码组织不合理时，可以及时调整，但不得借此扩大当前任务范围。

### 探索性实现

方案探索不要求遵循正式开发的 Type-Driven Development 或固定迭代方式，可以直接修改应用、运行实验原型、观察行为并调整实现。

探索期间仍须遵守项目级禁令，并维护任务进度记录。

准备将探索成果转为正式实现时，应整理临时代码，确认类型与职责边界，并完成正式开发要求的必要验证与 Review。

## 专项验证

正式开发完成后，根据变更的实际影响范围选择必要验证。

### 编译与静态检查

根据修改范围执行适用的 Cargo 检查，包括：

- Rust 格式检查。
- Cargo Workspace 编译检查或构建。
- Clippy 静态检查。
- Cargo 配置与依赖关系检查。

具体命令参见 `rules/common-commands.md`。

不要求对每项修改执行所有命令，但不得将未实际执行的检查标记为通过。

### 实际运行与行为验证

涉及运行时行为的修改，应根据实际情况直接运行应用，通过日志、调试工具、运行时状态和可观察结果检查目标行为。

对于无法通过静态检查确认的问题，应优先观察真实执行路径，不以编译成功代替行为正确性验证。

Bug 修复应尽可能在原有问题发生的真实场景中确认修复结果。

验证过程中不得编写测试、Benchmark 或 Example。具体限制遵循 `rules/project-context.md`。

### GUI 运行时验证

涉及可观察 GUI 行为新增或修改时，必须按照 `rules/gui-debugging.md`，使用 BRP 对实际运行的应用进行针对性自动验证。

BRP 验证允许执行自动化交互、截图、ECS 状态查询与日志检查，不属于禁止的测试代码。

验证应覆盖当前任务新增、修改及直接影响的 GUI 行为，不要求重新遍历无关的历史场景。

BRP 无法覆盖的行为，应根据实际情况选择适当的运行与调试方式，并如实记录验证边界。

### 独立 Code Review

达到触发条件的变更，必须按照 `rules/code-review.md` 完成独立 Code Review。

Code Review 用于检查实现中的具体问题，不替代编译、静态检查或必要的运行时验证。

## 验证范围与结果记录

验证以当前任务及其直接影响为范围，不要求执行无关场景的全量检查。

工具无法覆盖、运行环境不满足要求或验证执行失败时，应如实记录：

- 已执行的验证及实际结果。
- 尚未验证的行为与范围。
- 未能完成验证的具体原因。
- 仍然存在的问题或风险。

不得将未验证部分视为通过，也不得以不等价的检查方式冒充目标验证。

实际验证结果及 Code Review 结论统一记录在任务进度 Markdown 中。
