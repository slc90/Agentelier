# Agent 间消息与六个协作工具

Agent 间通信通过 Agent Control 进行。发送方只声明目标和消息语义，Control 负责目标解析、Mailbox、唤醒、执行状态与持久化。消息不会直接写入另一个 Agent 的内存历史。

## Mailbox 与消息投递

每个 Agent 有属于自身的 Mailbox。Mailbox 保存尚未消费的消息，并提供活动通知。消息应有稳定 ID、发送者、接收者、所属 Session、来源 Turn/call ID、投递模式、内容及创建顺序。消息内容遵循模型协议中的明文/加密内容语义，不在投影层擅自解密或改写。

消息投递至少区分：

- **QueueOnly**：将消息放入 Mailbox，不启动空闲 Agent。
- **TriggerTurn**：将消息放入 Mailbox，并让目标 Agent 处理当前活动 Turn 或在空闲时启动新 Turn。

Mailbox 在 Runtime 卸载期间仍然存在于可恢复状态。卸载时要先停止目标执行接纳，再将尚未消费的消息转移到持久化 Mailbox/会话事件；恢复后按原顺序交付。不能在执行环境关闭和新消息写入之间丢信。

Mailbox 在 Session 日志中分别保存接纳、领取和消费。消息按接纳序号排序，每个接收方最多保留 64 条待消费或已领取消息。同一消息 ID 与相同载荷返回原接纳序号，复用 ID 的不同载荷会被拒绝。已领取消息必须由同一接收方和 Turn 确认消费，从存档恢复时保留无确认的领取状态。

`spawn_agent` 的初始任务通过 `TriggerTurn` 消息接纳。Runner 只在对应消息已持久领取后开始执行，实际轮次终态获得确认后再保存消费记录。Runtime 在确认每次 Mailbox 变化后发布持久序号，供驻留执行体和协作等待订阅。

## 六个工具的行为契约

| 工具 | 目标 | 主要语义 | 是否唤醒空闲目标 |
|---|---|---|---|
| `spawn_agent` | 创建新 Agent | 任务、角色、Fork 和模型选项；创建独立身份及执行环境 | 是，创建后启动 |
| `send_message` | 已存在 Agent | 只投递消息，供目标当前执行或之后读取 | 否 |
| `followup_task` | 已存在 Agent | 投递后要求目标执行新一轮任务 | 是 |
| `wait_agent` | 当前调用者 | 等待 Mailbox/活动变化或超时 | 不适用 |
| `interrupt_agent` | 指定 Agent | 请求停止目标当前执行并等待/报告停止状态 | 否 |
| `list_agents` | 当前 Agent Tree | 查询 Agent 身份、路径、角色和状态 | 否 |

### send_message 与 followup_task

两者共享目标解析和消息投递路径，但投递模式不同。`send_message` 不能因为目标空闲就悄悄创建 Turn；消息留在 Mailbox，等后续 Follow-up 或恢复处理。`followup_task` 要求目标开始处理消息，目标运行中时将后续输入按目标 Agent 的输入接纳规则排队或合并，不并行启动第二个 Turn。

`send_message` 接受同一 Session 的 Agent ID 或完整路径，并拒绝向调用者自身投递。成功回执包含消息 ID、目标和接纳序号。活动 Runner 在已封闭工具调用的请求边界领取 QueueOnly 消息，将发送方及正文作为独立历史输入保存，之后确认消费并开始下一次模型请求。空闲目标保留待处理消息。

`followup_task` 为已有子 Agent 持久接纳 `TriggerTurn` 任务。活动目标在原轮次与工具回收后按顺序启动，空闲目标使用已保留的 Conversation 启动下一 Turn。唤醒时按顺序领取该任务之前的 QueueOnly 消息，每条输入保留发送方和来源。工具回执区分已安排的运行与排队，以及已接纳但缺少可恢复历史的待处理任务。

### wait_agent

Wait 订阅目标 Agent 的活动通知，然后等待消息、调用者 Steer 或超时。超时时间有默认值、最小值和最大值，模型请求的超时超出上限时拒绝，低于下限时按规则钳制并在结果中说明。等待必须使用事件/通知机制，不能高频轮询 Registry。

`wait_agent` 先订阅调用者自身 Mailbox 的持久序号，再检查待处理活动。默认等待 15 秒，范围为 50 毫秒到 60 秒。活动、已接纳的 Steer 与超时均有对应回执。工具取消释放订阅，其他 Agent 的运行由各自的控制令牌管理。

### interrupt_agent

Interrupt 针对一个目标 Agent 发出取消请求。工具结果需要区分请求已接纳、正在收尾、已真实停止和停止失败/未知。发送取消令牌不等于进程或 Runtime 已结束；执行容量只在真实回收后释放。

### list_agents

List 返回当前调用者可见的 Agent Tree 子集，至少包含路径、角色、状态和必要的父子关联。结果顺序稳定，避免模型每次看到不同顺序。列表不返回凭据、内部文件路径或未授权会话信息。

## 结果交付给父 Agent

子 Agent 完成后产生结构化完成事实，包含 Agent 身份、原始任务来源、终态、结果正文和必要错误摘要。父 Agent 通过内部活动通知得知结果；后续模型请求读取已确认的结果材料。子 Agent 不直接伪造 Root 的 Assistant 输出，也不把内部过程当成用户对话。

父 Agent 可以继续 Follow-up、等待或中断子 Agent。结果交付与子 Agent Runtime 是否继续驻留分开：完成结果保存后，Runtime 可以留驻等待后续任务，也可以在符合卸载条件时回收。

## 目标解析与访问边界

目标可以使用稳定 Agent ID 或 Agent Path。解析器必须拒绝空目标、模糊昵称、未知路径、跨 Session 目标和已删除目标。对已卸载 Agent 的消息操作应先恢复必要的控制状态或将消息排入持久 Mailbox，不要求为了发送 QueueOnly 消息而完整启动模型 Runtime。

## 消息与历史的一致性

消息投递必须有明确持久化确认边界。发送成功的工具回执只能在 Mailbox 已接纳消息后返回。重复接收同一消息 ID 应去重；不同内容复用同一 ID 是冲突。接收与消费状态必须可区分，避免 Runtime 崩溃后重复执行同一 Follow-up。

不把完整 Rollout Trace 纳入本次实现。持久化消息 ID、发送者、接收者、模式、顺序和消费事实，已足以支持必要的交付恢复与故障定位。
