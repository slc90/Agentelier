# 更新、恢复与压缩中的指令生命周期

基础快照属于会话设置，项目快照属于运行期上下文。会话目录不变，不代表项目规则内容也不变；一条任务内部的工具往返，同样可能跨过规则更新。

## 在模型请求边界刷新

每次新的逻辑模型请求之前，都沿会话目录重新发现并有界读取规则链。第一次提问、后续聊天、工具结果反馈之后的继续推理、排队任务真正开始、用户主动重试，都经过这个边界。

这里选择直接读取少量本地文件，不建立文件监控、定时轮询或只看修改时间的缓存。内容摘要用于决定是否向协议历史追加新项，不用于跳过必要的文件发现。这样既能发现原文件被编辑，也能发现原先不存在的中间层 `AGENTS.md` 被新建、删除或变为空文件。

这是本方案针对本地个人应用的简化选择。Codex 的项目发现缓存会根据环境选择、信任状态和预算等条件失效，并非同样的逐请求完整重读；参考的是其快照和变化通知思想。[Codex 刷新条件](sources.md#codex)

边界按一次模型请求计算，不按每个工具调用计算。同一响应提出的多个工具调用，仍按现有批次顺序执行并封闭结果；其中一个调用修改了 `AGENTS.md`，新规则在下一次模型请求生效，不追溯改变已经执行的调用，也不因此拆开函数调用与结果的配对关系。Stop 和 Steer 继续按现有控制语义工作。

## 成功采集、失败采集与取消是不同状态

成功取得空快照可以撤销旧规则；读取失败不能。失败时保留上一次快照作为历史核对材料，同时停止当前请求，显示文件和原因。不得静默发送旧规则，也不得把读取失败转换成移除通知。

项目读取错误属于可修复的任务失败。用户修好文件后，可以按原有资格重试或发送新消息，不要求重置会话。它不应被混同为协议历史损坏而永久设置 `execution_blocked`。存储提交不确定、历史不可恢复或工具收尾失败，则仍沿现有执行阻断路径处理。

加载发生在执行侧，使用有界文件读取，不在 Bevy 主线程读磁盘。取消后不启动新模型请求；已经开始的阻塞读取必须纳入真实回收，不能留下脱离任务的后台句柄。Runner 仍统一清理任务进程、关闭 Steer 接纳并发布终态。文件读取失败发生在工具步骤之后时，已有副作用和封闭结果继续保留，不把任务失败解释为撤销修改。

## 创建、重试和恢复各自保留什么

| 操作 | 基础指令 | 项目规则与历史 |
| --- | --- | --- |
| 新建会话 | 固定准备区的基础快照 | 首次请求才采集，未采集不显示为“无规则” |
| Reset | 按现有行为复制旧会话设置 | 创建新会话身份和空历史，下一请求重新采集 |
| 继续聊天或工具往返 | 使用同一快照 | 请求前重新采集，变化才追加 |
| 用户主动 Retry | 仍用会话原快照 | 重新采集当前文件；旧失败尝试的请求材料保留 |
| 同一次 HTTP 认证恢复重发 | 不变 | 不变，重发已冻结载荷 |
| 打开历史会话 | 恢复当时保存的基础快照 | 展示历史项目快照，不立即执行工具或发送请求 |
| 恢复后首次发送 | 不变 | 重新采集，必要时追加替换或移除通知 |
| Queue 中的输入开始执行 | 使用所属会话设置 | 开始执行时读取，不在入队时冻结项目规则 |

普通 Retry 的资格继续由已经提交的模型／工具步骤、已应用 Steer 等事实决定。新增一条自动项目上下文项，本身不算完成了一步模型任务，也不应单独禁止原本合法的 Retry。已经执行并提交工具步骤的任务仍通过新消息继续，防止重做副作用。

只在内存中更新项目状态不足以支持恢复。项目快照、上下文项及其请求归属必须通过现有会话日志保存。旧存档没有项目记录时，按“从未由客户端注入”开始；不推测旧聊天里是否包含类似规则，也不生成历史加载事实。

## 压缩会丢掉明文，不能丢掉当前规则

当前系统使用 Responses 的服务端 Inline compaction：保存完整响应，封闭所有工具结果，再提交并安装工作窗口检查点。基础快照仍由请求适配器单独提供。项目规则作为历史项进入压缩后，旧明文可能只留在不透明 compaction 项里。[当前压缩实现](sources.md#local) · [服务端压缩](sources.md#protocol)

因此，项目快照的完整内容必须独立于活跃工作窗口保留。每次成功安装新窗口后，标记“本窗口尚未明确发布项目状态”。下一请求先重新采集，然后在保留的原始窗口尾部追加一次完整当前规则，或在此前发布过项目规则而当前为空时追加清除说明。

```mermaid
flowchart LR
    H["旧工作历史：项目项、聊天与工具"] --> C["服务端 Inline 压缩"]
    C --> K["工具结果封闭并提交检查点"]
    K --> W["安装新工作窗口"]
    W --> N["下一请求前重新采集"]
    S["独立保存的项目状态与来源"] --> N
    N --> A["在新窗口尾部发布当前完整状态"]
```

即使文件没有变化，压缩后的第一次发布仍然必要：它保证模型能看到原文，而不只是压缩器对规则的记忆。同一窗口随后内容不变，不再重复。文件更新与窗口恢复同时发生时，合并成一条最新状态通知。

发布发生在检查点确认之后，不在待封闭的工具调用中间插入。保留 compaction 项及其后原始协议项的顺序，不解密、不改写其内容，也不以文本摘要替代。检查点保存失败时不提前切换窗口或清除发布状态；已有存储阻断语义保持不变。

恢复存档时，是否需要重新发布，要由已提交检查点和当前窗口中的项目发布记录共同确定。恢复到“检查点已提交、下一请求尚未开始”的位置，应在继续时恰好补一次，而不是漏掉或重复补入。

## 预算按真正发送的内容计算

项目文件的 32 KiB 上限控制一次当前快照的源材料大小。完整模型上下文另按所选模型的 token 窗口和压缩策略管理。

项目上下文正文、包装标题、路径说明和移除通知都通过协议历史参与 token 估算。候选更新在请求发送前计入，不能等返回后才发现超限。完整快照另有持久保存，不因此在 token 预算中再加一遍。

已有服务端用量锚点仍适用于原始历史前缀；追加的项目项作为新增尾部估算。普通更新不需要丢弃锚点。安装压缩窗口后沿用现有清除旧锚点的行为，重新计入新窗口中的实际材料以及基础前缀、工具定义。缓存输入量不从窗口占用中扣除。

不同历史版本的规则尚未压缩时，都是真实输入，必须全部计量。不能为了省 token 删除旧版本、裁剪旧工具结果，或改写已发送的用户消息。超过完整请求限制时明确失败；仍保留输入和已提交历史。
