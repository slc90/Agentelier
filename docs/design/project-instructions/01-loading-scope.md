# 从会话目录确定项目规则的范围

项目规则的起点不是聊天正文，也不是某条 Shell 命令碰巧进入的目录，而是会话已经保存的 `working_directory`。现有会话在创建时校验并固定这个目录，工具调用中的临时 `workdir` 不改变它。本方案沿用这项约定，见[当前实现依据](sources.md#local)。

## 先把三个目录概念分开

**会话工作目录**是创建会话时选定的本地目录，是自动发现的输入。**项目根目录**是从该目录向上找到的最近一个 `.git` 标记所在目录。**工具执行目录**只影响某次命令或进程，不自动成为新的会话工作目录。

`.git` 可以是目录，也可以是 Git worktree 使用的文件；这里只把它当作边界标记，不执行 Git 命令，不解析其中的配置。找不到标记时，只检查会话工作目录，不把磁盘根目录或某个父目录猜成项目根。不增加 `Cargo.toml`、`package.json` 等语言专属探测，避免把普通包目录误认成项目边界。

这沿用了 Codex 从项目根到当前工作目录建立指令链的思路，但没有搬入其可配置标记、多环境和备用文件名体系。[Codex 文件发现](sources.md#codex)

## 沿一条路径加载，而不是扫描整棵仓库

找到根目录后，从根到会话工作目录逐层检查 `AGENTS.md`，按父目录在前、子目录在后的顺序收集。只读取这条链上的文件，不越过项目根，不递归枚举兄弟目录或下级目录。

例如，会话工作目录是 `C:/work/game/src/ui`，项目根是 `C:/work/game`：

| 路径 | 自动加载结果 |
| --- | --- |
| `C:/work/AGENTS.md` | 不读取，位于项目边界之外 |
| `C:/work/game/AGENTS.md` | 读取，项目根规则 |
| `C:/work/game/src/AGENTS.md` | 读取，路径上的中间层规则 |
| `C:/work/game/src/ui/AGENTS.md` | 读取，当前目录规则 |
| `C:/work/game/src/backend/AGENTS.md` | 不读取，属于另一条目录分支 |
| `C:/work/game/src/ui/panels/AGENTS.md` | 不读取，位于当前目录之下 |

每份规则保留自己的来源文件和作用目录。根规则适用于项目树；子目录规则只约束对应子树。程序不删除父规则，也不把子规则的每句话解析成配置覆盖项。模型根据范围理解它们，发生自然语言冲突时结合直接用户要求处理。

### 在项目根工作，不等于自动加载全部子目录规则

如果会话工作目录是 `C:/work/game`，自动链只包含根目录的 `AGENTS.md`。模型随后修改 `src/ui`，并不会仅凭补丁路径或 Shell 参数让客户端自动切换到 UI 的规则链。

更深目录中的规则由模型借助已有本地工具按需查阅，例如遵循根文件中的文档导航，在修改 UI 前检查 UI 目录规则。该读取结果属于工具历史，不能在核对界面伪装成客户端自动加载的来源。

本阶段不解析任意 PowerShell 文本来推测任务范围，不拦截每个文件操作，也不新增会话中途切换目录的入口。需要另一条自动规则链时，通过现有准备区选择目录并新建会话。动态更新针对的是当前自动链的文件及边界变化，不是让程序猜测模型正在关注哪个模块。

## 文件内容保持为文件内容

只识别 `AGENTS.md`。同目录的 `AGENTS.override.md`、`CLAUDE.md` 和其他名称不参与候选选择。文件中的 Markdown 链接、规则导航与目录引用也不触发递归导入；模型根据任务决定是否读取所引用的资料。

读取使用 UTF-8，允许并去除一个文件开头的 UTF-8 BOM，其余正文保留，包括换行。纯空白文件不生成规则正文，但来源核对中可以说明它为空。解码失败不能用替换字符悄悄改写规则。

每份有效条目保存来源路径、作用目录、正文和内容摘要。整个快照还保存会话目录、项目边界、确定的条目顺序及模型可见文本摘要。比较以实际文本和范围为准，不以文件修改时间作为唯一证据；相同内容被重新保存，不应制造一次新的指令发布。

Windows 路径复用已有规范化语义。用于读取和比较的是路径值，显示时才使用路径显示库，不用显示字符串执行文件操作或用字符串前缀判断父子关系。源文件可以按普通文件读取语义跟随链接；这不引起额外目录遍历。失效链接、循环链接或不可读取目标按读取错误处理，不从其他目录补找规则。

## 一次采集有明确的大小和失败结果

当前规则链的源文件原始字节合计上限取 **32 KiB**。这是本方案采用的集中内部限制，不增加配置界面。读取必须有界，不能先无限读入内存，再检查长度；正文、来源标题及包装文字形成的实际请求还受原有完整请求大小限制约束。

这里选择超限时停止本次请求，而不是采用 Codex 的截断策略。半份工程规则可能删掉关键限制，完整失败比发送一份看似有效的残缺规则更容易理解。错误应指出文件、已用字节和总预算，用户可以精简常驻规则，把细节留在按需读取的项目文档中。

| 采集结果 | 含义与后续行为 |
| --- | --- |
| 未发现规则或文件为空 | 成功取得空快照，允许继续 |
| 找到完整规则链 | 成功取得有序快照 |
| 目录不可用、访问失败、非普通文件、编码错误或超限 | 本次采集失败，不发送新模型请求 |

查找根标记时遇到访问错误，也不能直接解释为“没有项目根”。文件在探测后消失，可以作为该次采集未发现处理；已经打开后读取失败则报告失败。下一次请求仍重新检查。

采集结果表示本次顺序读取取得的内容。运行中的编辑发生在采集之后，留到下一请求边界处理；不引入文件监控服务，也不宣称多份文件在磁盘上具有一个共同事务。
