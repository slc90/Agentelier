# 怎样验收异步边界

异步工具最容易出错的地方是两个合法事件交错之后，系统仍把它们解释成旧的串行顺序。本清单沿着响应接纳、执行、保存、历史追加、请求、前台结束和恢复逐项检查。每条都要求可以核对的结果；界面出现“完成”、HTTP 200 或构建成功，各自只能证明其中一部分。

以下项目均为待执行的验收要求，不是已通过的验证记录。执行方案把每组场景放到产生相应行为的功能增量中；最终跨 Turn 场景随最后一个实际功能增量收口，不另设没有实现产出的“验收阶段”。

## 先准备能区分真实行为的证据

### 目标环境与现有资料保护

运行验收使用 Windows x64、DX12、PowerShell 7、当前锁定依赖和真实应用。涉及模型服务的验证沿用现有 Sign in with ChatGPT 与 `gpt-6.2-sol`，不自动换模型、切登录路径或增加无目的的重复请求。编译、静态检查按本阶段改动选择；纯文档工作不冒称完成运行验收。[项目约束](../../../rules/project-context.md)、[常用命令](../../../rules/common-commands.md)规定了环境和检查范围。

在现有数据环境中通过正常应用创建专用验收会话，保留原有会话、登录和文件。可写命令限定在明确的验收工作目录；验证恢复前备份该验收会话的记录和必要附件。不要为了方便而重置整个数据目录、删除已有会话或复制认证材料。需要损坏数据的场景只处理已备份的验收记录副本，并明确记录应用实际读取哪份材料。

账号退出、切换、重新授权、凭据重置以及更换数据目录造成的登录失效，仍需要已有的明确授权。清单中的相关条目不授权执行这些动作；缺少授权时标为未执行，并保留可先完成的静态检查。普通关闭后使用同一数据环境重新打开，与退出账号分开处理。

不编写或引入测试、Benchmark、Example、mock 服务、专用 harness 或只为本清单服务的测试依赖。允许直接运行应用、使用其正常工具和诊断能力，以及调试器控制真实应用的边界。难以稳定触发的故障，可以在调试器中控制完成、回执或事件处理的时机；如果没有可用观察入口，就记录未覆盖的具体条件，不编造一次通过。[GUI 验证规则](../../../rules/gui-debugging.md)明确允许通过 BRP 自动操作真实应用。

### 四类证据不能互相冒充

| 标记 | 证据 | 能说明的范围 |
| --- | --- | --- |
| 静 | 实际源码、依赖方向、序列化分支、状态转换与错误路径审阅 | 说明规则已被表达；不能单独证明运行时交错、UI、进程或真实服务行为 |
| 调 | 调试器控制真实应用边界，或检查正常应用的诊断状态 | 说明应用在指定局部条件下的行为；人工替换的响应/事件必须注明注入位置，不称为服务实际返回 |
| 运 | 真实应用、正常工具调用、Session Store 记录、进程事实、关联日志；GUI 部分通过 BRP 实际输入和截图/ECS 查询 | 说明对应执行和交互确实发生；本地状态不能代替服务接收与模型使用结果的证据 |
| 服 | 真实 Responses 请求/响应的安全记录及关联结果，必要时由模型准确复述工具独有随机标记 | 说明当前接入路径和协议续接实际工作；不由一次 HTTP 200 推断整个应用生命周期正确 |

表中的“运＋调”表示真实应用场景需要同时观测或控制一个内部边界，不要求生成自动化测试程序。“服；异常分支调”表示正常协议要真实调用，难以让服务产生的非法输入只验证本地拒绝路径，两类记录必须分开。

每个条目记录：场景 ID、实际前提、操作、预期事件顺序、观察结果、证据位置、是否通过及清理结果。关联信息使用会话、来源 Turn、请求、任务、原始 `call_id` 和提交序号；不要用“第几张卡”代替身份。日志只保留必要的安全字段，不导出凭据、隐藏 reasoning/compaction 内容或完整敏感正文。[日志规则](../../../rules/logging.md)继续适用。

“空闲不自动请求”的计数专指聊天/工具结果续接请求。记录实际触发来源，排除用户显式 Queue 正常启动的 Turn 以及原有长期记忆后台请求；不能把它们误判为工具完成引发的自动聊天，也不能用混合总数掩盖新增续接。

未执行、故障条件未达到、证据不足都不标为通过。运行发现失败时，修复对应增量并复核直接受影响的场景；不因为换了一份计划就重跑全部无关检查。

### GUI 操作的完成条件

使用实际安装版本的 `bevy_brp_mcp` 发现应用和方法，优先按现有稳定 `Name` 找控件。Pointer、Keyboard、Focus、Scroll 都走真实输入；不得直接改 ECS 状态后声称用户交互通过。工具接受请求、Pointer 输入执行结束、目标 UI 行为正确分别核对。动态状态检查关键中间帧和最终收敛，不要求机械增加截图次数。

结束自动交互后，通过已发现的 `brp_extras/pointer_control` 执行 `release`，再查询 `status`，直到 `phase=inactive`，并检查 `last_error`。`busy=false` 不能单独证明 UI 成功。BRP 不具备等价能力的 OS 行为按真实环境另行观察；不得改用不等价的桌面输入冒充标准 BRP 验收。

## N · 原生协议与工具模式（9 项）

依据：[调用与协议](01-turns-and-calls.md)。正常路径需要真实服务证据；非法响应分支通过明确标注的本地调试验证，不要求服务主动制造非法数据。

| ID | 前提与动作 | 明确通过标准与证据 |
| --- | --- | --- |
| N-01 | 使用现有授权和 `gpt-6.2-sol` 创建新会话，检查实际发送的准备请求。 | `input` 首项为唯一的 developer `additional_tools`。顶层省略 `tools` 和 `previous_response_id`。叶子保留 schema 和实际声明模式，后续输入顺序保持，`store:false`、`stream:true`。证据：服＋静，安全请求检查记录。 |
| N-02 | 在同一工具目录分别调用异步资格工具、`apply_patch`、`write_stdin`、记忆修改与管理工具；检查 Extension/MCP 映射。 | 模式符合设计表，控制与修改工具保持同步；未知 Extension 不自动异步，MCP 原参数 schema 未被加上任务 ID；同一来源的契约一致。证据：静＋运；服务请求中的工具声明。 |
| N-03 | 取得一次真实原生异步调用，比较 SSE 完整调用项、最终响应和持久记录。 | `async:true`、`call_id`、输出项 `id`、名称和完整参数一致保留。完成响应通过校验并持久确认后才派发。结果使用原 `call_id` 的 `function_call_output`。证据：服＋运。 |
| N-04 | 对已声明异步的调用，在调试器中分别令最终模式缺省和为 `false`；保持身份与载荷一致。 | 两者均按同步依赖处理，下一请求等待真实结果；记录返回模式，不擅自当作原生异步。注入材料单独标为本地分支验证。证据：调＋静。 |
| N-05 | 分别构造同步声明收到 `async:true`，以及 SSE 完整项与最终项的身份、名称、参数或模式冲突。 | 在完整响应正常提交、任务登记和派发之前拒绝整份响应；该批无任何工具副作用。错误保留具体冲突，不能以最终值静默覆盖。证据：调＋静，执行开始记录为空。 |
| N-06 | 在完整调用项到达后暂停最终响应；随后分别正常完成、断流、收到失败/非法完成。 | 暂停阶段只展示，不启动工具；只有完整合法响应和持久登记确认后才能派发。失败/非法分支不执行此前已显示的调用。证据：运＋调，必要的真实 SSE 记录。 |
| N-07 | 对同一调用重复投递完全相同的完整流项/完成事实，再提供同 ID 不同载荷的冲突；检查同批及既有历史中的 ID。 | 相同事实幂等合并，调用只启动一次；同批重复调用身份、历史重用或载荷冲突均明确拒绝，不靠新的任务 ID 绕过去重。证据：调＋运，调用账本和开始记录。 |
| N-08 | 打开缺少模式字段的旧同步会话；检查其他明确模型的请求路径，并观察真实声明拒绝或本地等价错误分支。 | 旧会话按保存的同步契约绑定，不静默升级；其他模型保持同步；服务拒绝显示实际错误，不自动换模型、改登录或重发另一套工具契约。来源/schema 不匹配仍拒绝执行。证据：运＋静；有真实拒绝时附服，否则注明局部验证。 |
| N-09 | 对新会话核对按名称绑定、再次请求与重开后的冻结目录和原始历史。调试未知工具、意外 namespace 和 SSE/最终 namespace 冲突。另打开旧平铺同步存档。 | 每次从同一冻结目录生成一个 `additional_tools` 首项，材料索引对应实际 `input`。原始调用参数和历史字段原样保留。非法调用在派发前拒绝。旧存档沿用平铺，正式路径须取得服务证据。证据：服＋运，异常分支调。 |

## O · 唯一会话权威与接纳（6 项）

依据：[唯一历史](02-history-and-delivery.md)。这一组关注业务状态和并发接纳；UI 的具体呈现在 U 组验证。

| ID | 前提与动作 | 明确通过标准与证据 |
| --- | --- | --- |
| O-01 | 审阅一次前台推进、后台完成和存储回执经过的实际所有者；运行时观察状态归并。 | Conversation 保留唯一会话状态和历史；Runner 只持局部/冻结材料，完成时不整份归还旧 Session；Tools 不直接写 UI/日志存储，Conversation 不持 OS 句柄或 JoinHandle。证据：静＋调。 |
| O-02 | 在额度充足的响应与任务映射提交前、提交中、确认后暂停，查询可见任务并观察派发。 | 应用生成的任务 ID 随完整响应和映射原子提交，确认前不公开、不派发；确认后获准后台调用与任务一一对应。中断后不存在只保存响应却丢失映射的半状态。证据：调＋运，连续提交记录。 |
| O-03 | 在前台流式更新/终态归还附近，交错执行旧任务结果提交、会话改名和 Queue 入队。 | 当前正文、旧任务结果、名称和 Queue 各自保留最新有效事实；没有整份旧快照覆盖；恢复后的记录与实时状态一致。证据：运＋调，前后业务快照和提交序号。 |
| O-04 | 暂停一个真实存储回执，让控制输入和正常凭据协调事件到达，再释放回执。 | Runtime 能接纳控制和凭据事件，尚未开始的派发可被停止；相关业务提交仍有序，已提交操作不因等待被遗忘或盲重写。取消不是磁盘确认。证据：调＋运，接纳与回执时序；不主动破坏账号。 |
| O-05 | 将发送/Steer 与前台 final 的接纳关闭放在边界两侧，并尝试同时发起结果处理。 | 始终至多一个活动 Turn；输入要么已接纳并被明确应用/终结，要么拒绝且保留草稿；不存在 Accepted 后消失、同一输入既 Steer 又新建 Turn。证据：运＋调，接纳回执、Turn 身份和请求集合。 |
| O-06 | 让旧执行实例或其他会话的迟到完成抵达当前所有者；另投递本会话旧 Turn 的有效完成。 | 无效实例/会话不能改当前账本；同会话旧 Turn 的有效结果仍按稳定任务身份归并。来源 Turn、请求与 `call_id` 不变，任务 ID 不因终态或恢复而复用。证据：调＋运，身份核对及资源收尾记录。 |

## D · 开放历史与结果交付（8 项）

依据：[结果与请求的排序](02-history-and-delivery.md)。必须核对原始协议事实与实际请求，不能只看任务列表。

| ID | 前提与动作 | 明确通过标准与证据 |
| --- | --- | --- |
| D-01 | 保留一个尚未完成的异步调用，在后续请求中继续完整历史；任务完成后提交其结果。 | 未配对调用可以合法保留，原始输出及不透明推理材料有序重放；结果只向原 `call_id` 追加一次。找不到原调用、身份不符时不发送孤立 output。证据：服＋运，历史位置与结果集合。 |
| D-02 | 请求 R 发出后让旧任务 A 完成并保存；随后 R 正常完成。 | A 可先持久保存，但历史顺序为 R 的合法原始输出在前、边界追加 A 的 output 在后；R 的请求记录不声称含有 A。多个就绪结果按业务提交序号追加。证据：运＋调，冻结前缀和追加序号。 |
| D-03 | 冻结并开始发送请求后，交错接纳 Steer、Queue、后台结果和展示更新。 | 在途字节/摘要、历史覆盖范围和结果集合不变；新材料只影响后续合法边界。未启动 Queue 不进入当前请求，不能靠重新序列化偷偷更新正在发送的请求。证据：运＋调，准备与发送记录。 |
| D-04 | A 在 R 进行期间完成，随后令 R 失败、停止或缺失合法完整输出。 | R 的非法/部分输出不安装为正常历史；A 在保留前缀的合法边界完成归并，不永久等待缺失的 `response.completed`。部分展示仍可保留且状态准确。证据：运＋调。 |
| D-05 | 对同一结果重复通知/重复归并，再提供同身份不同结果；另抑制一次唤醒并进入请求或等待边界。 | 相同结果不重复追加、不重执行；不同结果阻断续接并保留冲突；边界重新检查账本能发现已就绪事实，不依赖一次通知。证据：调＋运，唯一 output 和错误记录。 |
| D-06 | 依次停在结果形成、保存、追加、请求准备、发送、完整成功各边界；发送后再中断响应并明确继续。 | 各状态独立且真实；发送未知不标成功。后续重放已有结果不新增 output、不重跑工具；原有副作用/已保留步骤的整 Turn Retry 限制仍生效。证据：运＋调；正常成功路径附服。 |
| D-07 | 异步 `view_image` 返回真实图片，观察附件提交、结果记录、历史追加与后续请求。 | 附件先保存，结果持有不可变会话附件身份；请求使用同一图片内容，UI 摘要/截断不改变协议载荷；原调用只配一个结果。证据：运＋服，附件摘要、提交顺序和安全请求投影。 |
| D-08 | 将已确认结果放在 final 之前、final 接纳关闭附近及空闲之后分别到达；空闲时暂不操作。 | 合法下一请求可用的结果被正常携带；已经收束的 final 不被强迫重新采样。空闲只保存/追加并提示待处理，不增加完成通知触发的聊天续接请求；下一次用户输入或明确结果动作再消费。证据：运＋调，按触发来源计数。 |

## R · 持久化、恢复与崩溃窗口（11 项）

依据：[保存与恢复](04-durability-and-context.md)。这些场景仅操作专用验收会话，使用同一登录和数据环境。可用调试器在所列已确认位置暂停，再结束应用并重开；无法到达该位置时保留未覆盖状态。重复加载检查包含唯一占位和唯一结果，不需要重跑工具。

| ID | 前提与动作 | 明确通过标准与证据 |
| --- | --- | --- |
| R-01 | 在仅有 RequestPrepared 或部分 SSE、尚无完整合法响应时结束应用，再打开会话。 | 恢复发送/部分展示事实，不生成可执行新调用，不把屏幕上半个调用当作已接纳任务；没有自动模型请求。证据：运＋调，恢复记录与请求/执行计数。 |
| R-02 | 响应和任务映射已持久确认，执行开始记录尚未确认时结束并恢复。 | 原任务恢复为 NotExecuted，为原调用补唯一的未执行 output；来源和任务 ID 保持不变，没有真实副作用或自动重启。再次加载不新增第二份占位。证据：运＋调。 |
| R-03 | 分别在开始记录确认后但实际副作用之前、实际副作用之后但结果保存之前结束并恢复。 | 两种情况均按已知证据标为 Unconfirmed，不靠未看到产物猜测未执行；补明确未知说明，不自动重跑。已有副作用原样保留，终止说明不伪造成功。证据：运＋调，开始记录和可观察产物。 |
| R-04 | 图片附件确认保存后、对应工具结果未确认时结束并恢复。 | 文件存在不被当作结果成功；任务按结果未确认处理，不从附件反推一份成功 output；正常会话其他附件与原件不被覆盖。证据：运＋调，附件和结果记录对照。 |
| R-05 | 实际结果已经保存，尚未追加 output 时结束并恢复。 | 从已存载荷恢复并补唯一 output，内容/附件身份一致；不调用执行器补结果。重复打开仍只有一份。证据：运＋调，载荷摘要和执行计数。 |
| R-06 | output 已追加、下一请求尚未准备时结束并恢复。 | 显示已保存待处理，结果仍按原调用关联；恢复不自动发聊天续接请求，用户明确继续后正常携带。原有记忆后台请求另计来源。证据：运＋调；续接正常路径附服。 |
| R-07 | 包含结果的请求已开始发送，但完整响应未保存时结束并恢复，再明确继续。 | 原请求标为结果未知，已有历史和 output 保留；后续可重放同一结果，工具执行和 output 追加各仍一次；不声称网络恰好交付一次。证据：运＋服或明确标注的传输调试。 |

## 完成记录怎样保留

每个实施增量保留它负责场景的实测结果和必要复核，不只写“测试通过”。一份有效记录应能回答：哪一个任务在什么确认边界到达，系统当时保存了什么、发送了什么、执行了什么，最终有没有剩余资源，以及观察者凭什么得出结论。

若某项仅完成静态审阅或本地注入，明确保留该证据范围。特别是官方协议接入、真实非阻塞续接、Windows 进程回收和实际 GUI 行为，分别需要对应的服、运与 BRP 证据。整个功能不能因清单已经写全就被宣称验收完成。
