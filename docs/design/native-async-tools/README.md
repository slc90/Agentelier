# 原生异步工具：从继续聊天到可靠交付结果

本文组是待实施的目标设计。当前实现仍以一个 Turn 持有执行上下文、逐批封闭调用与结果为基础；这里提出的跨 Turn 行为，需要完成对应实施方案后才成为应用事实。既有模块文档继续说明当前实现。

从一个具体场景开始：用户让模型启动耗时工作 A，模型先回答能够独立回答的部分。A 没结束，用户继续发言；新的 Turn 又启动工作 B。B 先完成，A 后完成。用户应该能继续输入、看清两项工作的状态，并在后续回复中得到正确结果。A 的结果始终属于 A，不能因为界面已经进入新的 Turn 而消失，也不能被误当作 B 的结果。

这个场景需要同时改变三件事：工具调用可以暂时没有结果；工具的生命周期可以长于一次前台 Turn；结果要通过会话自己的历史和存储边界进入后续请求。本文按这个顺序展开，再讨论取消、进程、恢复、压缩和界面如何保持一致。

## 既有依据与本方案的选择

退役前，使用同一 Sign in with ChatGPT 登录和 `gpt-6.2-sol` 下的四组对照确认了 `additional_tools` 路径。服务返回 `async: true` 的调用项，在结果缺席时回答了独立问题，随后按原 `call_id` 收到并使用真实结果。以上为迁移前的实验。当前新建 Codex `gpt-6-astra` 会话通过 WebSocket 顶层工具声明接入异步，历史 SIWC 声明继续用于存档读取。[协议与对照记录](sources.md)

此前已经确定的范围是 Direct Mode、现有登录路径、单活动 Turn、同一会话内多项跨 Turn 异步工作，以及现有 Steer、Queue 交互。本方案把尚未具体化的行为收束如下。

| 边界 | 本方案采用的行为 |
| --- | --- |
| 原生协议 | 以 developer `additional_tools` 首项提供冻结的 Function Tool 目录，同一目录包含同步工具与具备异步资格的工具 |
| 前台与后台 | 一个会话至多一个活动 Turn；前台正常结束后，已接纳的异步调用与进程资源可以继续存在 |
| 空闲时结果完成 | 保存、更新任务状态并提示待处理；继续聊天或点击“处理已完成结果”后再发聊天请求，不因完成通知自行启动聊天续接 |
| Stop | 停止当前 Turn，并取消它创建的未结束工具与进程；更早 Turn 的后台工作保留，可单独取消或停止全部后台工作 |
| 会话切换 | 当前会话仍有活动执行、待回收资源、未保存结果或已开始的存储提交时，拒绝切换、Reset 和删除；说明阻塞来源。正常保存且没有活资源后，可以带着待处理结果切走 |
| 启动工具 | 第一版在完整响应校验和持久提交之后派发；SSE 中的完整调用项用于展示与一致性检查 |
| 等待任务 | 应用分配稳定任务 ID，以同步管理工具查询、等待与取消；不修改任意 MCP 工具的原始参数结构 |
| 恢复 | 恢复数据和未交付的已存结果；不自动重新执行历史工具、不恢复操作系统进程、不自动发模型请求 |
| 压缩 | 达到压缩阈值时，等待未配对调用的结果保存并追加。调用闭合后恢复 Inline 压缩 |

这些是应用行为的设计选择，不是 Responses API 替应用管理后台任务的承诺。后台工作也始终限定在当前单进程、单内存会话的范围内。
